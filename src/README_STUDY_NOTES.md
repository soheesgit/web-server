# 학습 노트: PNG 처리 흐름으로 읽는 서버 구조

이 노트는 사용자가 준 [요청·응답 구조도 PNG](<C:/Users/locka/OneDrive/Desktop/web network/스크린샷 2026-11-20 오후 7.29.39.png>)의 순서를 본문 목차로 삼는다. 먼저 클라이언트 요청이 내려가고 응답이 돌아오는 전체 흐름을 따라간다. 각 단계 안에서 관련 함수, 구조체, 주석을 쉬운 말로 설명하고, 표는 뒤에서 이름을 찾아볼 때 쓴다.

그림에는 `app`, `engine`, `router`, `handler`, `upstream`도 나온다. 이번 작업 범위는 처음 요청한 대로 `downstream`과 `common`이다. 그 밖의 상자는 그림에 적힌 역할만 연결 지점으로 설명하며, 해당 소스 내부 동작은 확인한 사실처럼 다루지 않는다.

그림의 색은 `downstream` 보라색, `upstream` 초록색, 실행·라우팅·처리기 회색, 공용 `common` 빨간색이다. 소스 설명은 보라색과 빨간색 영역에 집중하고, 나머지는 전체 화살표를 이해하는 데 필요한 만큼만 다룬다.

## 핵심 요약

- **`common`은 HTTP 규칙을 처리한다.** 요청과 응답에서 공통으로 쓰는 헤더 파싱, 본문 길이 판정, 본문 경계 추적, keep-alive 판정, 상태 문구를 제공한다. 소켓 I/O는 하지 않는다.
- **`downstream`은 클라이언트 연결을 처리한다.** 대기 소켓에서 연결을 받고, 요청을 파싱한 뒤 라우터·처리기에 맡기고, 응답을 클라이언트로 전송한다.
- **`conn`이 두 영역과 외부 처리기를 연결한다.** 수신 버퍼에 바이트를 모으고, 요청 파서와 공용 규칙을 호출하고, 응답 계획을 받아 실제 송신과 자원 정리를 맡는다.
- **요청 처리 순서:** 연결 수락 → 요청 머리 파싱 → 본문 수신 → route 선택과 처리기 호출 → 응답 계획 작성 → 응답 송신 → 연결 유지 또는 종료.
- **현재 범위의 한계:** 요청 chunked 본문은 501로 거부한다. v2 이벤트 경로의 비동기 CGI·프록시는 미완성이라 해당 요청에 500을 반환한다.
- **검증 상태:** 이 문서는 코드와 기존 디렉토리 문서를 바탕으로 썼다. 빌드, 테스트, 실제 네트워크 동작은 확인하지 않았다.

## PNG 흐름을 따라가는 전체 처리 과정

그림은 두 방향을 한 장에 보여준다. **요청은 클라이언트에서 아래의 처리 경로로 내려가고, 응답은 같은 연결을 타고 클라이언트로 돌아간다.** 프록시 요청만 업스트림 서버를 거치는 추가 왕복이 있다.

```text
요청: 클라이언트 → downstream 연결 → 요청 파싱 → router → handler
응답: handler → response_plan_t → downstream 응답 작성·본문 전송 → 클라이언트
프록시 갈래: handler → upstream 연결·backend → 응답 머리·본문 → response_plan_t
공용 규칙: common이 요청·응답의 헤더와 본문 경계를 해석하고 출력 형식을 만든다
```

### 1. `app`이 서버 구성 요소를 준비한다 — 그림의 맥락

PNG 맨 위의 `app/` 상자는 `main`이 설정과 각 구성 요소를 조립한다는 뜻이다. 이 노트에서는 `app`의 소스는 조사하지 않았으므로, 어떤 설정 파일을 읽고 스레드를 어떻게 만드는지는 설명하지 않는다. 아래 단계는 `app`이 대기 소켓과 연결 처리 환경을 준비한 뒤부터 시작한다.

그림 맨 아래의 `core/`는 문자열(`str`), 버퍼(`buf`), 로그(`log`), 설정(`config`), 플랫폼별 기능(`platform`)이 여러 영역에 쓰인다는 뜻이다. 이번 설명은 이 타입들이 등장하는 지점만 다루고, 그 내부 구현까지 내려가지는 않는다.

### 2. `downstream/listener`가 클라이언트 연결을 받는다

그림의 보라색 대기 소켓은 새 연결을 기다리는 소켓이다. `listener_open`은 주소와 포트에 이 소켓을 열고, `listener_accept`는 연결 요청 하나를 받아 실제 통신용 소켓(fd)을 돌려준다. 이 소켓은 `conn_new`로 넘어간 뒤 한 클라이언트의 연결 상태에 속한다.

그림의 `conn fd × N`은 연결마다 `conn_t`가 하나씩 있다는 뜻이다. `conn_t` 안에는 받은 요청 바이트를 담는 `rbuf`, 아직 보내지 못한 응답 바이트를 담는 `wbuf`, 현재 요청과 응답 계획, 상태, 마감 시각이 들어 있다. 즉, 같은 클라이언트의 여러 read/write 호출이 와도 지금 어느 단계인지 잊지 않게 해주는 상태 보관함이다.

그림 가운데 `engine/`은 많은 연결 중 준비된 fd를 알려주는 층이다. `conn` 인터페이스는 v1 blocking 방식과 v2 non-blocking 이벤트 방식을 구분하지만, 엔진의 스레드 풀·이벤트 루프 구현은 이번 코드 범위에서 확인하지 않았다.

### 3. `conn`이 요청 바이트를 모으고 머리 끝을 찾는다

TCP는 요청 한 개씩 경계를 보존해 전달하지 않는다. 요청 머리가 여러 번에 나뉘어 오거나 다음 요청 일부가 같은 수신 버퍼에 붙을 수 있다. `conn`은 `rbuf`에 바이트를 모으고 `request_parse_head`를 다시 호출해 머리가 완성됐는지 확인한다.

`http_find_head_end`는 헤더 뒤의 빈 줄을 찾아 머리 끝을 알려준다. 빈 줄까지 바이트가 도착하지 않았으면 `HTTP_PARSE_INCOMPLETE`다. 아직 요청이 잘못된 게 아니므로 더 읽는다. 제한 크기를 넘기거나 형식이 틀리면 오류 결과와 상태 코드를 돌려준다.

### 4. 요청 줄·헤더·URI를 `http_request_t`로 만든다

머리 끝이 확인되면 `request_parse_head`가 시작 줄과 헤더를 해석한다. 시작 줄에서 메서드, 대상 URI, HTTP 버전을 분리하고, `http_parse_headers`로 `이름: 값`을 검사해 헤더 목록을 만든다. HTTP/1.1 요청에는 Host 헤더가 하나 있어야 한다. 문법 오류는 400, 지원하지 않는 버전은 505 등으로 구분한다.

URI는 `uri_split`으로 경로와 query를 나누고, `uri_decode_path`로 `%XX` 표기를 풀고, `path_normalize`로 `.`·`..`과 중복 `/`를 정리한다. 예를 들어 `/docs/./intro%20page?lang=ko`는 라우팅용 path `/docs/intro page`와 query `lang=ko`가 된다.

**그림과 실제 함수 호출 순서의 차이:** PNG는 본문 길이·수신 뒤에 URI 정규화를 배치하지만, 코드에서는 `request_parse_head`가 머리 처리 중 URI를 먼저 나누고 정리한다. 그리고 Content-Length를 확인한 뒤 `conn`이 본문을 받는다. 따라서 그림은 연결 관계의 지도이고, 실제 순서는 코드 설명을 따른다.

### 5. 본문 길이를 정하고 요청 본문을 받는다

`http_resolve_framing`은 헤더를 보고 본문이 없는지, Content-Length만큼인지, chunked인지 등을 판정한다. PNG의 `CL / chunked`는 이 판정을 가리킨다. Content-Length와 Transfer-Encoding이 동시에 있거나 서로 다른 길이 값이 있으면 모호한 요청을 피하려고 거부한다.

현재 요청 파서는 chunked 요청을 501로 거부한다. Content-Length 방식이면 `conn`이 그 길이만큼 `rbuf`에 모은 뒤 `req.body`에 연결한다. `http_body_track`은 별도의 공용 도구로, 업스트림 응답 같은 본문 조각을 전달하며 끝 위치를 추적할 때 쓴다.

요청의 문자열 값은 수신 버퍼를 복사하지 않고 가리킨다. 그래서 `conn`은 처리 중 `rbuf`를 지우거나 재할당하지 않는다. 파이프라이닝으로 다음 요청 바이트가 이미 와 있으면 이번 요청이 사용한 머리와 본문만 소비하고 나머지는 남겨둔다.

### 6. `router`가 경로와 Host로 handler를 고른다 — 그림의 연결 경계

완성된 `http_request_t`에서 라우팅에 쓰는 값은 Host와 정규화한 path다. PNG의 router 상자는 이 값과 설정 규칙으로 STATIC, CGI, REVERSE PROXY 중 처리기를 고른다고 표시한다. `conn`은 route가 없으면 404 계획을 만들고, 있으면 `handler_dispatch`에 요청을 건넨다.

라우터의 우선순위와 실제 규칙은 그림에 자세히 나와 있지 않고, 이 작업에서는 라우터 소스도 살펴보지 않았다. 따라서 특정 URL이 어느 handler에 가는지는 이 노트만으로 답할 수 없다.

### 7. 선택된 handler가 응답을 준비한다 — PNG에 나온 세 갈래

아래 세 갈래는 **PNG에 적힌 처리 흐름을 읽기 쉽게 풀어 쓴 것**이다. handler 소스의 실제 세부 구현을 확인한 설명은 아니다.

- **STATIC:** 그림은 GET·HEAD만 허용하고 다른 메서드는 405로 보내는 흐름을 그린다. root와 정규화 경로를 결합하고 root 밖으로 나가는 경로는 403으로 막는다. 파일을 못 열면 404 또는 403, 디렉터리에 index가 없으면 403으로 이어진다. MIME·길이·수정 시각 헤더를 정한 뒤 결과 본문을 `BODY_FILE`로 넘긴다.
- **CGI:** 그림은 `cgi-bin` 스크립트를 확인하고 환경 변수를 만든 다음 stdin/stdout pipe를 열고 자식 프로세스를 실행하는 순서다. POST 본문은 stdin으로 전달하고, CGI가 돌려준 상태·Content-Type 헤더를 읽는다. 헤더가 잘못되면 502로 이어지며 결과 본문은 `BODY_PIPE`로 넘긴다.
- **REVERSE PROXY:** 그림은 route의 upstream 그룹에서 backend를 고르고, 연결을 얻어 요청을 보내고, 응답 머리를 받은 뒤 본문을 중계한다고 표시한다. backend 선택은 round-robin, 연결 실패 시 다음 backend 시도, 요청을 이미 보냈는지에 따른 오류 구분이 그려져 있다. 결과 본문은 `BODY_UPSTREAM`으로 연결된다.

이 세 handler는 모두 `response_plan_t` 형태로 downstream에 응답을 넘긴다. 이 공통 경계가 있어 downstream은 본문 내용이 파일·프로세스·backend 중 어디서 왔는지에 따라 다른 전송 방법을 고를 수 있다.

#### REVERSE PROXY가 upstream을 거치는 세부 흐름 — PNG 기준

이 순서는 그림에 그려진 초록색 경로를 읽어 쓴 것이다. `upstream/` 소스는 작업 범위 밖이라 실제 함수 이름과 각 분기의 실행 여부는 확인하지 않았다.

1. router가 선택한 route에서 upstream 그룹을 얻는다.
2. 연결 풀에서 재사용 가능한 keep-alive 연결을 찾거나 backend에 새 연결을 얻는다. 그림은 round-robin으로 backend를 고르고 장애가 난 backend를 제외하는 흐름을 나타낸다.
3. downstream 요청을 backend가 받을 형태로 바꾼다. 그림에는 origin-form 요청 줄로 바꾸기, hop-by-hop 헤더 빼기, Host와 X-Forwarded-For 헤더 추가가 표시돼 있다.
4. 연결을 얻지 못하면 다른 backend를 시도한다. 연결을 얻은 뒤 요청을 보낸다. 그림에서는 backend가 요청 바이트를 받은 뒤 생긴 실패를 502 갈래로 나타낸다.
5. backend 응답의 상태 줄과 헤더를 읽는다. 응답 머리 대기가 늦으면 그림의 경로는 504로 간다. 응답 헤더에서 hop-by-hop 항목을 빼고 Content-Length·chunked·연결 종료 중 본문 경계를 판단한다.
6. `http_response_t`에 업스트림 응답 머리 정보를 담고 남은 본문 길이를 기록한다. 본문을 버퍼에 전부 모으는 대신 정해진 길이만큼 downstream으로 전달한다. chunked면 `http_body_track`이 조각 경계를 따라간다.
7. downstream은 이 응답을 `BODY_UPSTREAM` 계획으로 이어받아 클라이언트에 전달한다. 응답 본문을 다 읽었는지와 backend keep-alive 여부가 연결 재사용 판단에 영향을 준다.

그림의 초록색 상자들은 처리 흐름 전체를 설명하는 참고다. 이 노트에서는 `http_headers`, `http_framing`, `http_body_tracker_t`, `http_response_t`, `response_plan_t`처럼 범위 안에서 연결되는 부분을 중심으로 읽는다.

### 8. `response_plan_t`를 downstream이 실제 응답으로 바꾼다

`response_plan_t`는 상태와 추가 헤더를 가진 `head`, 본문 출처를 고르는 `kind`, 출처별 데이터와 소유 자원을 담는다. `BODY_MEM`은 버퍼, `BODY_FILE`은 파일 fd와 보낼 구간, `BODY_PIPE`는 CGI pipe, `BODY_UPSTREAM`은 backend 연결과 본문 경계 추적기를 사용한다.

`response_write_head`는 상태 줄·Date·Server·추가 헤더·Content-Length나 chunked 표시·Connection 정책을 출력 버퍼에 만든다. `http_reason`은 상태 코드의 이름을 제공한다. HEAD나 본문이 없어야 하는 상태에는 본문 길이 헤더 규칙을 다르게 적용한다.

예를 들어 계획의 상태가 200이면 상태 줄은 `HTTP/1.1 200 OK`가 된다. 날짜 값은 요청마다 달라지고, 본문 길이와 연결 헤더는 계획과 클라이언트 버전에 따라 정해진다.

그다음 `conn`이 계획의 본문을 전송한다. 메모리·파일은 저장된 바이트나 구간을 보내고, CGI·업스트림은 읽은 조각을 이어서 보낸다. chunked 응답에는 `response_write_chunk`와 `response_write_last_chunk`가 조각과 끝 표시를 붙인다. 본문 전송이 시작된 뒤 실패하면 새 오류 상태를 보낼 수 없어 연결을 닫는다.

### 9. 응답 뒤 연결을 유지하거나 정리한다

`http_keep_alive`는 HTTP 버전과 Connection 헤더를 읽어 연결 유지 판단에 필요한 값을 돌려준다. `conn`은 여기에 응답의 close 표시, 연결당 최대 요청 수, 서버 종료 상태를 더해 최종 결정을 한다.

연결을 유지하면 현재 요청이 사용한 바이트만 `rbuf`에서 제거한다. 다음 요청이 이미 버퍼에 있으면 바로 다시 3단계로 간다. 닫을 때는 `plan_cleanup`, `proxy_job_cleanup`, `conn_free`가 본문 자원, 자식 프로세스, backend 연결, 버퍼와 소켓을 정리한다.

헤더·본문 수신 중 마감 시간이 지나면 408, 프록시 응답 대기 시간이 지나면 504를 계획할 수 있다. 클라이언트가 전송 중 끊어지면 중계 자원을 회수한다. 이런 분기와 마감은 그림의 단순 화살표에는 모두 나오지 않아 `conn.h`의 처리 순서와 `conn.c` 설명을 보완해서 읽는다.

## 보조 예시: HTTP 요청 하나로 단계 확인

앞의 PNG 단계가 이 문서의 중심이다. 다음 요청은 그 단계를 코드 이름과 연결해 보는 가상 입력이며, 실제 서버에 보냈거나 테스트에서 관측한 결과가 아니다.

```http
POST /docs/./intro%20page?lang=ko HTTP/1.1
Host: example.test
Content-Length: 4

DATA
```

### 1. 연결을 받고 바이트를 모은다

`listener_open`은 서버가 기다릴 TCP 소켓을 만든다. `listener_accept`가 클라이언트 하나를 받아 fd를 돌려주면, `conn_new`가 그 fd를 소유하는 `conn_t`를 만든다. 이때 v1은 timeout이 있는 blocking 방식, v2는 non-blocking 방식을 사용하도록 설정된다.

`conn`은 클라이언트에서 읽은 바이트를 `rbuf`에 모은다. TCP는 HTTP 요청 단위로 데이터를 전달하지 않는다. 위 요청이 요청 줄·헤더·본문 세 번으로 나뉘어 올 수도 있고, 다음 요청의 일부가 `DATA` 뒤에 함께 올 수도 있다. 그래서 한 번의 `read`가 곧 한 요청이라고 가정하지 않는다.

`conn_t`는 연결의 작은 작업 공간이다. `rbuf`에는 받은 요청 바이트, `wbuf`에는 아직 보내지 못한 응답 바이트가 있다. 현재 요청은 `req`, 현재 응답 계획은 `plan`, 프록시 재시도 상태는 `job`에 둔다. 연결의 현재 단계와 다음 timeout도 함께 들고 있어, 이벤트가 오면 `conn`이 어디서 이어서 처리할지 알 수 있다.

### 2. 요청 머리와 본문을 분리한다

빈 줄은 요청 머리의 끝이다. 예시에서는 `Content-Length: 4` 다음의 빈 줄까지가 머리이고, 그 뒤 네 바이트 `DATA`가 본문이다.

`conn`은 `request_parse_head`를 호출한다. 이 함수는 머리 끝을 찾을 때 `http_find_head_end`를 쓰고, 헤더 줄을 나눌 때 `http_parse_headers`를 쓴다. 요청이 덜 도착했다면 파서는 오류를 만들지 않고 `HTTP_PARSE_INCOMPLETE`를 돌려준다. `conn`은 다음 입력을 읽은 뒤 다시 파싱한다. 형식이 틀렸다면 `HTTP_PARSE_ERROR`와 응답 상태 코드를 돌려준다.

완성되면 파서는 첫 요청만 `http_request_t`에 담는다. 다음 요청 바이트가 수신 버퍼에 이미 있어도 `head_len`은 첫 요청 머리의 끝을 가리킨다. 요청 안의 `str_t` 값은 문자열 사본이 아니라 `rbuf`의 일부를 가리키므로, 요청 처리가 끝나기 전에 버퍼를 움직이거나 다시 할당하면 안 된다.

파서 결과의 세 상태는 서로 다른 뜻이다. `DONE`은 이 요청 머리가 준비됐다는 뜻이고, `INCOMPLETE`는 잘못된 입력이 아니라 바이트를 더 받아야 한다는 뜻이며, `ERROR`는 입력을 더 받아도 해결되지 않는 규칙 위반이다. 일반적인 오류 상태는 잘못된 문법 400, 본문 한도 초과 413, 대상 URI 한도 초과 414, 머리나 헤더 수 한도 초과 431, 지원하지 않는 메서드나 chunked 요청 501, 지원하지 않는 HTTP 버전 505다.

### 3. 대상 주소를 라우팅에 쓸 형태로 바꾼다

예시의 메서드는 `POST`, 대상은 `/docs/./intro%20page?lang=ko`, 버전은 HTTP/1.1이다. 파서는 메서드와 버전을 확인한 뒤 대상 처리에 `uri.c`의 함수를 사용한다.

`uri_split`은 경로와 query를 가른다. 이 예시에서는 경로가 `/docs/./intro%20page`, query가 `lang=ko`다. `uri_decode_path`가 `%20`을 공백으로 바꾸고, `path_normalize`가 `.` 경로 요소를 제거한다. 따라서 라우터에 넘길 path는 `/docs/intro page`가 된다. query는 별도 값으로 유지된다. 프록시가 원본 경로 표기를 필요로 할 수 있어 요청 구조체에는 정규화 경로와 원본 경로를 따로 둔다.

HTTP/1.1의 origin-form 요청에는 Host 헤더가 하나 필요하다. 파서는 헤더 목록에서 Host를 확인하고 `http_request_t`에 host를 채운다. 여기서 문서가 설명하는 범위는 이 값이 `conn`을 통해 라우터에 넘어가는 지점까지다. 어떤 route가 선택되고 그 route가 무슨 응답을 만드는지는 라우터·처리기 영역의 책임이다.

### 4. 본문 길이를 정하고 요청 처리를 시작한다

`http_resolve_framing`은 `Content-Length: 4`를 보고 본문 방식이 `FRAMING_LENGTH`, 길이가 4라고 기록한다. `conn`은 이 네 바이트가 모일 때까지 본문 timeout을 적용해 읽는다. 네 바이트가 다 모이면 `req.body`가 그 구간을 가리키고, 그제야 요청을 라우터와 처리기에 넘긴다.

요청 파서는 현재 chunked 요청을 받아들이지 않고 501로 거부한다. 공용 `http_body_track`이 chunked 형식도 추적할 수 있다는 사실과 혼동하지 않는다. 그 추적기는 업스트림 응답처럼 바이트 조각을 전달하면서 본문 끝을 찾아야 하는 곳에서 쓰인다.

길이 방식은 “본문이 4바이트에서 끝난다”처럼 끝 위치를 Content-Length로 바로 안다. chunked 방식은 각 조각 앞의 16진수 길이를 따라가야 한다. 예를 들어 `4\r\nDATA\r\n0\r\n\r\n`은 4바이트 데이터 조각 뒤에 끝 조각이 오는 모양이다. `http_body_track`은 여러 번 나눠 들어온 이 조각들을 추적하고, 본문 뒤에 붙은 다음 메시지 바이트는 현재 본문에 포함하지 않는다.

### 5. 처리 결과를 응답 계획으로 받고 바이트를 보낸다

`conn`은 `router_match(host, path)`로 경로에 맞는 route를 찾고, `handler_dispatch`에 요청을 전달한다. 맞는 route가 없으면 `conn`은 404 응답 계획을 만든다. route가 있으면 처리기가 `response_plan_t`를 채운다. 이 계획에는 상태 코드와 헤더, 본문이 메모리·파일·CGI pipe·업스트림 중 어디에서 오는지가 들어간다.

`response_plan_t`는 응답을 직접 보내는 함수가 아니라 전송할 내용을 설명하는 묶음이다. `head.status`와 `head.fields`에 상태와 추가 헤더를 담고, `kind`가 본문 출처를 고른다. `BODY_MEM`이면 `body.mem.data`가 바이트를 갖고, `BODY_FILE`이면 fd·시작 위치·길이를 갖는다. `BODY_PIPE`는 CGI pipe와 자식 프로세스를, `BODY_UPSTREAM`은 프록시 대상 연결과 본문 추적 상태를 가진다. 계획은 그 자원들의 소유자이기도 해서 응답 뒤 `plan_cleanup`이 회수한다. `conn`이 계획을 실행하는 역할과 처리기가 계획을 만드는 역할을 나누는 이유가 여기에 있다.

설명만을 위해 처리기가 상태 200과 메모리 본문 `OK`를 계획했다고 가정해 보자. 이것은 실제 처리기 결과를 확인한 것이 아니다. `response_write_head`는 계획에서 상태와 헤더를 읽어 응답 머리 바이트를 만든다. 이 함수가 만드는 상태 줄은 `HTTP/1.1` 형식이며, 필요한 날짜·서버·본문 길이·연결 헤더를 붙인다. 그다음 `conn`이 계획에 적힌 본문 출처에서 바이트를 읽어 클라이언트에 보낸다.

본문 출처에 따라 실제 전송 방법은 다르다. 메모리는 버퍼에서 복사하고, 파일은 지정된 구간을 보내고, CGI pipe와 업스트림 응답은 읽은 조각을 계속 중계한다. chunked로 보낼 때는 `response_write_chunk`로 각 조각을 감싸고 끝에 `response_write_last_chunk`를 쓴다.

### 6. 연결을 재사용하거나 자원을 정리한다

응답이 끝나면 `conn`은 요청의 keep-alive, 응답 계획의 close 표시, 처리한 요청 수를 보고 소켓을 유지할지 결정한다. HTTP/1.1은 `Connection: close`가 없으면 보통 유지하고, HTTP/1.0은 `keep-alive`를 요청했을 때 유지한다. 유지할 경우 이번 요청의 머리와 본문 바이트만 `rbuf`에서 소비한다. 뒤에 다음 요청이 남아 있으면 별도의 새 연결 없이 바로 다시 파싱한다.

처리가 끝나면 프록시 작업과 응답 계획의 자원을 정리한다. `response_plan_t`가 파일 fd, CGI 자식 프로세스, 업스트림 연결을 소유할 수 있으므로 정리는 단순히 구조체 메모리를 비우는 일이 아니다. 각 자원을 닫거나 회수해야 한다.

### 중간에 실패하면 어떻게 되나

- 요청 머리가 아직 도착 중이면 연결은 기다린다. 머리 형식이 잘못됐거나 크기 제한을 넘으면 해당 오류 상태로 응답하고 연결을 닫는다.
- 헤더·본문 마감이 지나면 timeout 경로로 간다. 헤더나 본문 수신 중 timeout은 408이다. 요청 사이에 아무 입력 없이 idle timeout이 나면 응답 없이 닫는다.
- 라우트가 없으면 404 응답 계획을 만든다. 프록시 실패는 실패 이유와 재시도 정책에 따라 다시 시도하거나 502·503·504 응답 계획으로 끝난다.
- 클라이언트 응답 머리를 이미 보낸 뒤 CGI·파일·업스트림 본문 전송이 실패하면 별도 오류 응답을 붙일 수 없다. 연결을 닫고, 필요한 자원을 회수한다.
- 클라이언트가 처리 중 연결을 끊으면 `conn`은 CGI 자식과 업스트림 연결 같은 자원을 정리한다.

이 흐름은 `conn.h`의 처리 순서 주석과 `conn.c`의 연결 상태 구현에 적혀 있다. 단, 위의 `OK` 응답은 이해를 위한 가상 예시이며 테스트 통과나 실서버 관측을 뜻하지 않는다.

## 다시 찾아볼 낱말

앞의 흐름을 읽다가 낯선 단어가 나오면 아래 표에서 뜻을 확인한다. 표는 흐름을 대신하는 설명이 아니라, 읽다가 막힌 용어를 찾아보는 용도다.

| 낱말 | 이 코드에서 뜻하는 것 |
| --- | --- |
| 요청(request) | 클라이언트가 보내는 시작 줄, 헤더, 선택적인 본문. 예: `GET /hello HTTP/1.1` |
| 응답(response) | 서버가 보내는 상태 줄, 헤더, 선택적인 본문. 예: `HTTP/1.1 200 OK` |
| 헤더(header) | `Host: example.test`처럼 요청이나 응답의 부가 정보를 담는 이름과 값 |
| 머리(head) | 본문 앞부분. 요청 줄이나 상태 줄, 헤더, 마지막 빈 줄까지를 가리킨다 |
| 소켓(socket) | TCP 연결을 통해 상대와 바이트를 주고받는 운영체제 자원 |
| fd(file descriptor) | 프로세스가 소켓, 파일, pipe 같은 자원을 가리킬 때 쓰는 정수 번호 |
| 버퍼(buffer) | 아직 처리하거나 보내지 않은 바이트를 임시 보관하는 메모리 |
| 파싱(parse) | 받은 바이트를 요청·헤더 같은 구조로 나누고 규칙을 검사하는 일 |
| 직렬화(serialize) | 구조체의 값을 HTTP가 정한 바이트 순서로 만들어 내는 일 |
| 본문 경계(framing) | 본문이 몇 바이트인지, 청크 형식인지, 연결 종료까지인지 정하는 규칙 |
| chunked | 본문을 여러 조각으로 보내며 각 조각 앞에 16진수 길이를 붙이는 방식. 길이 0인 조각이 끝을 나타낸다 |
| hop-by-hop 헤더 | 현재 연결에만 적용되어 프록시가 다음 서버로 그대로 넘기면 안 되는 헤더 |
| origin-form / absolute-form | 요청 대상 표기 방식. `/path`로 시작하는 형식과 `http://host/path`처럼 scheme(통신 방식 이름)과 host까지 포함한 형식 |
| 빌림(borrow) | 구조체가 바이트를 복사하지 않고 다른 버퍼의 일부를 가리키는 것. 원본 버퍼가 바뀌거나 해제되면 그 포인터도 더 쓸 수 없다. |
| 계획(plan) | 응답 내용을 만들기보다, 응답 머리와 본문을 어디서 가져올지 기록한 `response_plan_t` |
| 업스트림(upstream) | 프록시가 요청을 전달하는 뒤쪽 서버 |
| upstream 그룹 | 하나의 route가 사용할 수 있도록 묶인 backend 후보들 |
| backend | 프록시 요청을 실제로 받아 처리하는 서버 한 대 |
| round-robin | 후보 backend를 차례대로 돌아가며 고르는 방식 |
| 연결 풀(connection pool) | 열린 upstream 연결을 보관해 다시 쓰는 공간 |
| X-Forwarded-For | 프록시가 원래 클라이언트 IP를 뒤쪽 서버에 전달할 때 쓰는 헤더 |
| CGI | 별도 자식 프로세스를 실행해 응답을 받아오는 방식 |
| blocking / non-blocking | blocking 호출은 I/O가 진행될 때까지 기다리고, non-blocking 호출은 지금 할 수 있는 만큼 진행한 뒤 기다릴 이벤트를 돌려준다 |
| 라우터(router) | 요청의 host와 path를 보고 어느 처리기로 보낼지 고른다 |
| 처리기(handler) | 선택된 요청에 어떤 응답을 만들지 정해 `response_plan_t`에 기록한다 |
| 이벤트 엔진(engine) | non-blocking 연결에서 어떤 fd를 기다릴지 등록하고 이벤트를 전달한다. 내부 구현은 이 문서 범위 밖이다 |

| [`common/`](common/README.md) | 요청과 응답이 함께 쓰는 HTTP 헤더, 본문 길이, 연결 유지 규칙과 경계 타입을 처리한다. | 소켓이나 파일을 읽고 쓰지 않는다. |
| [`downstream/`](downstream/README.md) | 클라이언트 소켓을 받아 요청을 읽고, 다른 영역에 처리를 맡기고, 응답을 전송한다. | 응답 내용 자체를 정하는 라우팅·처리기 정책을 소유하지 않는다. |

`common` 함수는 주어진 바이트와 구조체를 계산·변환한다. `downstream/conn.c`가 실제 I/O와 시간 제한, 자원 정리를 담당한다. 따라서 프로토콜 규칙을 볼 때는 `common`, 연결이 언제 읽고 쓰는지 볼 때는 `conn`부터 읽는다.

## 관련 주제는 이렇게 연결된다

- **수신에서 요청 객체까지:** `listener`가 연결을 받고 → `conn`이 바이트를 `rbuf`에 모으고 → `request_parser`가 머리를 해석하고 → `http_headers`와 `http_framing`이 헤더와 본문 규칙을 확인하고 → `uri`가 route에 넘길 path를 만든다.
- **요청 객체에서 응답 계획까지:** `conn`은 `http_request_t.host`와 정규화된 `path`를 라우터에 넘긴다. 선택된 처리기는 `response_plan_t`에 응답 상태, 헤더, 본문 출처를 기록한다. 라우터와 처리기 내부 결정은 이 작업 범위에서 다루지 않는다.
- **응답 계획에서 소켓 송신까지:** `response_writer`가 응답 머리의 바이트를 만들고, `conn`이 메모리·파일·CGI pipe·업스트림 중 계획에 기록된 출처에서 본문을 보낸다.
- **프록시 응답의 본문 길이:** `proxy_job_t`가 요청과 시도 상태를 담고, 응답 framing 규칙과 `http_body_tracker_t`가 중계할 본문 끝을 찾는 데 연결된다. 실제 relay와 backend 선택 정책은 범위 밖이다.
- **오류와 연결 수명:** 파서 오류와 timeout은 오류 응답 계획 또는 종료로 이어진다. 응답 머리를 이미 전송한 다음 본문 송신이 실패하면 새 상태 코드를 보낼 수 없어 연결을 닫는다. `plan_cleanup`과 `proxy_job_cleanup`은 계획과 시도 상태가 소유한 자원을 회수한다.

## 다시 찾아보는 공용 타입: `common/types.h`

### 값과 상태를 나타내는 열거형

| `proxy_fail_t` | 프록시 시도에서 연결·송신·응답 대기·응답 형식 중 어디서 실패했는지 나타낸다. |
| `proxy_next_t` | 프록시 실패 뒤 다른 백엔드로 재시도할지, 오류 응답으로 끝낼지 나타낸다. |

### 요청·응답과 진행 상태를 담는 구조체

| 타입 | 담는 내용과 쓰임 |
| --- | --- |
| `http_header_t` | 헤더 한 개의 이름과 값. 값은 원본 수신 버퍼를 빌린다. |
| `http_headers_t` | 헤더 여러 개를 받은 순서대로 담는다. 같은 이름의 헤더도 합치지 않는다. |
| `http_framing_t` | 본문을 읽는 규칙과 길이를 담는다. |
| `http_limits_t` | 요청 머리, URI, 헤더 수, 본문에 적용할 상한을 전달한다. |
| `http_body_tracker_t` | 여러 조각으로 받은 본문에서 현재 위치와 끝을 추적한다. 본문 바이트를 복사하지 않는다. |
| `http_request_t` | 요청 메서드, 원래 대상, 정규화된 경로, query, 헤더, 본문 길이 규칙, 연결 유지 정보를 담는다. `body`는 머리 파서가 아니라 `conn`이 채운다. |
| `http_response_t` | 업스트림 응답의 상태 줄, 헤더, 본문 규칙, 연결 재사용 정보를 담는다. |
| `http_head_out_t` | 클라이언트에 보낼 상태 코드, 추가 헤더, 본문 규칙, 연결 종료 표시를 담는다. |
| `response_plan_t` | 응답 머리와 본문 출처를 묶는다. 파일 fd, CGI pipe와 자식, 업스트림 연결처럼 동적으로 소유한 자원은 `plan_cleanup`이 정리한다. |
| `proxy_job_t` | 프록시가 보낼 직렬화 요청, 대상 그룹과 현재 백엔드, 시도 수, 요청을 보냈는지 여부를 담는다. 그룹과 백엔드 포인터는 빌린다. |

수명 규칙이 중요한 이유: 요청의 `str_t` 필드는 수신 버퍼 내부를 가리킨다. `conn`이 요청 처리를 끝내기 전에 버퍼를 이동하거나 재할당하면 그 포인터가 깨질 수 있다. 반대로 `response_plan_t`는 여러 fd와 버퍼를 직접 소유하므로 응답이 끝날 때 정리해야 한다.

## 함수 이름을 다시 찾을 때: `common/` 파일과 공개 함수

아래 표는 다른 소스 파일에서도 부를 수 있는 공개 함수를 중심으로 정리한다. 각 `.c` 파일 안에서만 쓰는 `static` 보조 함수는 외부 호출 대상이 아니며, 함수 바로 위의 소스 주석에서 역할을 설명한다.

### `http_headers.h` / `http_headers.c`

헤더의 끝을 찾고, 헤더 줄을 파싱하고, 이름으로 검색하고, 전달할 헤더 줄을 출력한다.

| 함수 | 역할 |
| --- | --- |
| `http_find_head_end` | 입력 바이트에서 시작 줄과 헤더가 끝나는 빈 줄을 찾는다. 아직 덜 왔으면 추가 입력을 요청한다. |
| `http_parse_headers` | 헤더 영역을 이름·값 쌍으로 나눈다. 잘못된 줄이나 너무 많은 헤더는 오류로 처리한다. |
| `http_header_get` | 이름이 같은 첫 헤더를 대소문자 구분 없이 찾는다. |
| `http_header_count` | 이름이 같은 헤더가 몇 개인지 센다. Host 중복 검사 등에 쓰인다. |
| `http_token_valid` | 메서드나 헤더 이름처럼 token 문법을 따라야 하는 문자열을 검사한다. |
| `http_is_hop_by_hop` | 한 연결에만 적용되는 헤더인지 판정한다. 프록시가 헤더를 전달할 때 제거 여부를 정하는 데 쓰인다. |
| `http_headers_write` | 헤더 목록을 `Name: value\r\n` 모양으로 출력 버퍼에 복사한다. 선택하면 hop-by-hop 헤더를 뺀다. |

### `http_framing.h` / `http_framing.c`

헤더를 보고 본문을 어디까지 읽을지 정하고, 본문이 조각나 도착해도 경계를 추적한다.

| 함수 | 역할 |
| --- | --- |
| `http_resolve_framing` | Transfer-Encoding과 Content-Length를 검사해 본문 읽기 방식을 정한다. 둘이 함께 있거나 서로 다른 길이가 있으면 거부한다. 응답은 HEAD와 1xx·204·304 상태 규칙도 적용한다. |
| `http_body_tracker_init` | 추적기를 특정 본문 길이 방식으로 초기화한다. |
| `http_body_track` | 새 바이트 중 현재 본문에 속하는 양을 세고 끝을 찾는다. 다음 메시지에 속한 바이트는 사용하지 않는다. |
| `http_keep_alive` | HTTP 버전과 Connection 헤더를 보고 연결을 계속 쓸지 판단한다. `close`가 있으면 종료한다. |

### `http_status.h` / `http_status.c`

| 함수 | 역할 |
| --- | --- |
| `http_reason` | 숫자 상태 코드에 대응하는 사유 문구를 돌려준다. |
| `http_error_body` | 상태 코드와 사유 문구로 간단한 HTML 오류 본문을 출력 버퍼에 덧붙인다. Content-Type 헤더는 호출자가 추가한다. |

## 함수 이름을 다시 찾을 때: `downstream/` 파일과 공개 함수

### `listener.h` / `listener.c`

| 함수 | 역할 |
| --- | --- |
| `listener_open` | 주소와 포트에 TCP 대기 소켓을 만들고 listen 상태로 둔다. |
| `listener_accept` | 대기 중인 클라이언트 연결 하나를 받는다. |
| `listener_port` | 대기 소켓에 실제로 연결된 포트를 돌려준다. 포트 0으로 열었을 때 배정 포트를 알아내는 데 쓴다. |
| `listener_close` | 대기 소켓을 닫는다. |

### `request_parser.h` / `request_parser.c`

`request_parse_head`는 시작 줄과 헤더를 검사해 `http_request_t`를 만든다. 메서드, HTTP/1.0·1.1 버전, 대상 URI, Host 개수, 본문 크기 상한, keep-alive 규칙을 적용한다. 본문 데이터는 읽지 않는다. 더 많은 입력이 필요한 상황과 오류 응답 상태도 호출자에게 구분해 돌려준다.

### `uri.h` / `uri.c`

| 함수 | 역할 |
| --- | --- |
| `uri_split` | URI 대상을 경로와 query로 나눈다. 퍼센트 디코딩은 하지 않는다. |
| `uri_parse_absolute` | `http://host/path` 형태에서 authority와 나머지 경로를 나눈다. |
| `uri_decode_path` | 경로의 `%XX`를 한 번 디코딩한다. 잘못된 escape와 NUL 결과를 거부한다. |
| `path_normalize` | 연속 `/`, `.`, `..`를 정리하고 경로가 루트 위로 올라가는지 검사한다. |

요청 파서가 이 함수들을 차례로 부른다: 대상에서 authority·경로·query를 구분하고, 경로를 한 번 디코딩한 뒤 정규화한다. query는 경로 파일 이름처럼 정규화하지 않는다.

### `response_writer.h` / `response_writer.c`

| 함수 | 역할 |
| --- | --- |
| `response_write_head` | 상태 줄과 날짜, 서버 이름, 응답 헤더, 본문 길이 규칙, 연결 헤더를 출력 버퍼에 쓴다. |
| `response_write_chunk` | 본문 데이터 한 조각을 chunked 형식으로 출력한다. |
| `response_write_last_chunk` | chunked 본문 끝을 나타내는 `0\r\n\r\n`을 출력한다. |

### `conn.h` / `conn.c`

`conn_t`는 내부가 헤더에 드러나지 않는 연결 객체다. 내부 버퍼와 현재 요청·응답 계획, 마감 시각, 자원 소유권을 `conn.c`가 관리한다.

| 함수 | 역할 |
| --- | --- |
| `conn_new` | 소켓과 실행 환경을 받아 연결 상태를 만든다. 성공하면 소켓 fd 소유권은 `conn`으로 옮겨간다. |
| `conn_free` | 연결과 연결이 소유한 버퍼, 응답 자원, 프록시 작업, fd를 정리한다. |
| `conn_serve_blocking` | v1 방식으로 연결을 닫을 때까지 요청과 응답을 순서대로 처리한다. |
| `conn_on_event` | v2 방식으로 한 fd 이벤트에서 가능한 만큼만 진행하고 다음 대기 상태를 돌려준다. |
| `conn_on_timeout` | 현재 단계의 마감이 지난 경우 응답을 만들지, 연결을 닫을지 결정한다. |
| `conn_fd` | 연결의 클라이언트 소켓 fd를 조회한다. |
| `conn_deadline_ms` | 다음에 적용할 마감 시각을 조회한다. |

`conn_status_t`는 엔진이 클라이언트 읽기, 클라이언트 쓰기, 다른 fd 대기 중 무엇을 해야 하는지, 연결을 정리해야 하는지 나타낸다. `conn_env_t`는 모든 연결이 공유하는 설정, 요청 한도, 라우터, 이벤트 엔진 포인터를 제공한다.

## 현재 구현에서 주의할 범위

- 요청 본문은 Content-Length 방식만 받는다. 공용 `http_body_track`은 chunked 추적 기능도 제공하지만, 요청 파서는 chunked 요청을 501로 거부한다.
- v1 blocking 경로는 CGI pipe와 업스트림 프록시 응답 본문 중계를 연결한다.
- v2 이벤트 경로는 메모리·파일 응답을 처리한다. 비동기 CGI와 프록시 fd 진행은 아직 연결되지 않아 해당 요청에 500을 돌려준다.
- 오류 본문을 만들 때 상태 줄과 헤더를 먼저 보내고, 본문 소스가 파일·pipe·업스트림이면 `conn`이 그 소스에서 전송한다.
- 다른 영역의 실제 구현과 서버 전체 실행은 여기서 확인하지 않았다. 이 안내만으로 전체 서버가 실행된다고 판단하면 안 된다.

## 이 범위에서 답할 수 있는 질문

- **요청 파서가 본문까지 읽나?** 아니다. `request_parse_head`는 요청 머리까지만 파싱하고 본문은 `conn`이 받는다.
- **본문이 덜 도착하면 오류인가?** 아니다. 파서는 `HTTP_PARSE_INCOMPLETE`를 돌려주고 `conn`이 더 읽은 뒤 다시 호출한다.
- **`str_t` 문자열을 왜 요청 처리 중에 보존해야 하나?** 요청의 문자열 필드가 수신 버퍼를 복사하지 않고 가리키기 때문이다.
- **요청 본문 크기는 누가 제한하나?** `http_limits_t.max_body` 한도를 요청 파서가 머리 단계에서 확인하고, `conn`이 선언된 길이만큼 받는다.
- **응답 계획은 직접 응답을 보내나?** 아니다. 응답 내용을 표현한다. `response_writer`와 `conn`이 계획을 바이트로 바꿔 전송한다.
- **연결이 다음 요청에 재사용되는지는 누가 판단하나?** `http_keep_alive`가 HTTP 버전과 헤더를 보고 판단에 필요한 값을 제공하고, `conn`이 요청 수와 응답 종료 조건까지 합쳐 최종 결정을 한다.

## 이 자료만으로 답할 수 없는 질문

아래 질문은 현재 문서와 `common`·`downstream` 소스만으로 단정하지 않는다. 필요한 영역의 코드나 실행 결과를 확인해야 한다.

- **“이 URL이 실제로 어떤 route와 handler에 연결되나?”** route 목록과 매칭 우선순위는 라우터 구현·설정에 달려 있다.
- **“어떤 요청이 정적 파일, CGI, 프록시 중 어디로 가나?”** 선택 규칙과 응답 생성은 처리기 구현에 있다.
- **“백엔드를 어떤 순서로 선택하고 언제 재시도하나?”** 공용 타입에는 상태가 있지만, backend 선택과 relay 실패 정책의 세부 동작은 upstream·handler 영역에 있다.
- **“v2는 이벤트를 어떤 운영체제 API로 기다리며 워커를 어떻게 배치하나?”** 이벤트 엔진과 서버 시작 경로는 이 문서 범위에 없다.
- **“v2 CGI·프록시 경로는 어떤 상태 머신으로 완성할 예정인가?”** 현재 코드에서 해당 경로가 미연결이고 500으로 처리된다는 점만 확인했다. 후속 설계는 확인하지 않았다.
- **“이 코드가 빌드되고 테스트를 통과하나, 실제 서버에서 동작하나?”** 이번 작업에서는 빌드·테스트·실서버 실행을 하지 않았다.
- **“헤더·본문 제한이나 timeout 값은 왜 그 수치인가?”** 값은 코드에서 확인할 수 있지만, 그 값을 택한 근거는 현재 범위 문서에서 확인되지 않았다.

## 코드에서 확인한 내용과 아직 확인하지 않은 내용

**코드와 기존 디렉토리 문서에서 확인한 내용:** 함수 목적, 입력·출력 형태, 경계 타입 수명, 요청 처리 단계, v1과 v2의 CGI·프록시 차이.

**이번 문서 작업에서 확인하지 않은 내용:** 빌드 성공, 테스트 결과, 실제 네트워크에서의 요청·응답 동작. 실행 검증은 하지 않았다.

테스트 이름과 단계 목록은 각 디렉토리의 [`common/README.md`](common/README.md)와 [`downstream/README.md`](downstream/README.md)를 참고한다. README의 테스트 이름은 검증 계획이며, 이번 문서 작성에서 실행한 결과가 아니다.

## PNG 단계 설명을 보완하는 파일별 주석 찾아보기

이 절은 `src/common/`과 `src/downstream/`의 C·헤더 주석 내용을 파일별로 설명한다. 소스의 전문 용어나 원문 주석을 길게 옮기지 않고, 그 주석이 독자에게 알려주려는 일을 풀어 쓴다. 소스 코드는 수정하지 않았다.

### `common/types.h` — 요청과 응답을 담는 상자

이 헤더는 여러 폴더가 같은 요청·응답 정보를 주고받도록 공용 타입을 모아 둔다. 타입 이름만 봐서는 언제 채워지고 누가 정리하는지 알기 어려워서 수명 설명도 함께 있다.

- `http_method_t`는 GET·HEAD·POST 중 어떤 요청인지 저장한다. 나머지 메서드는 현재 처리 대상이 아니다.
- `http_parse_result_t`는 파서가 끝났는지, 더 받을 입력이 있는지, 잘못된 입력을 만났는지 알려준다.
- `http_framing_kind_t`와 `http_framing_t`는 본문 끝을 찾는 방법을 저장한다. 길이 숫자가 있으면 그만큼 읽고, NONE이면 본문이 없으며, CHUNKED면 조각 길이를 따라간다.
- `http_body_result_t`와 `http_body_tracker_t`는 본문을 여러 번에 나눠 읽을 때 현재 어디까지 읽었는지 기억한다. 바이트를 복사하는 버퍼는 아니다.
- `http_header_t`는 헤더 하나, `http_headers_t`는 헤더 목록이다. 목록은 받은 순서를 유지하고 같은 이름의 헤더도 남긴다.
- `http_limits_t`는 요청 머리, URI, 헤더 개수, 본문에 허용할 최대 크기를 모은다.
- `http_request_t`는 파싱된 요청이다. 원본 대상과 정리된 경로를 함께 보관한다. 문자열은 수신 버퍼를 가리키고, `path` 배열만 구조체 안에 직접 저장된다. 본문은 머리 파서가 아니라 연결 처리기가 채운다.
- `http_response_t`는 프록시 대상 서버에서 받은 응답 머리를 담는다.
- `http_head_out_t`는 클라이언트에 보낼 상태 코드와 추가 헤더, 본문 전달 방식을 담는다.
- `body_kind_t`와 `response_plan_t`는 응답 본문을 메모리·파일·CGI pipe·업스트림 중 어디서 가져오는지 나타낸다. 계획이 fd나 프로세스를 소유할 수 있어 응답을 마친 뒤 `plan_cleanup`으로 정리한다.
- `proxy_fail_t`, `proxy_next_t`, `proxy_job_t`는 프록시 시도의 실패 이유, 재시도 여부, 현재 시도 상태를 기록한다.

구조체 안의 대표 필드도 이렇게 읽으면 된다.

- `http_header_t.name/value`는 헤더의 왼쪽 이름과 콜론 오른쪽 값이다. `http_headers_t.v/n`은 실제 헤더들이 들어 있는 배열과 현재 개수다.
- `http_framing_t.kind/length`는 본문 읽기 방식과 길이다. `http_limits_t.max_head/max_uri/max_headers/max_body`는 각 입력이 넘으면 안 되는 상한이다.
- `http_body_tracker_t.f`는 현재 본문 방식, `remaining`은 아직 읽어야 할 양, `state`는 chunked 본문을 읽는 내부 단계다.
- `http_request_t.method`는 요청 방식, `target`은 받은 주소 표기, `raw_path`는 원래 경로, `path`는 디코딩·정리 후 라우팅에 쓸 경로, `query`는 `?` 뒤 값이다. `minor`는 HTTP/1.0 또는 1.1의 끝 숫자, `head_len`은 머리 길이, `body`는 연결 처리기가 모은 본문이다.
- `http_response_t.status/reason/minor`는 업스트림의 상태 코드·사유 문구·HTTP 버전이다. `headers`, `framing`, `keep_alive`, `head_len`은 응답 헤더·본문 끝 규칙·연결 재사용 여부·응답 머리 길이를 담는다.
- `http_head_out_t.status/fields/framing/close`는 클라이언트에 보낼 응답 코드·추가 헤더 줄·본문 규칙·응답 뒤 연결 종료 여부다.
- `response_plan_t.head`는 응답 머리, `kind`는 본문 출처다. `body.mem`, `body.file`, `body.pipe`, `body.upstream` 중 `kind`에 맞는 하나만 사용한다. `head_pending`은 CGI 응답 머리를 아직 받아야 한다는 표시다.
- `proxy_job_t.group/backend`는 프록시 대상 그룹과 현재 서버, `request`는 보낼 요청 바이트, `attempts/max_attempts`는 지금까지 시도한 횟수와 한도, `sent_any`는 현재 시도에서 바이트를 보냈는지 나타낸다.

### `common/http_headers.c`와 `.h` — 헤더 줄 읽기와 쓰기

HTTP 헤더는 `이름: 값` 형식의 줄이다. 이 파일은 수신 바이트에서 헤더가 끝나는 위치를 찾고, 한 줄씩 검사해 목록으로 만든다. 여기서는 소켓에서 읽지 않는다.

- `ascii_lower`, `str_eq_ci_lit`, `str_eq_ci_view`는 대소문자를 무시하는 비교를 돕는다. 예를 들어 `Host`와 `host`를 같은 이름으로 보게 한다.
- `trim_ows`는 헤더 값 양끝의 공백과 탭을 잘라낸다.
- `http_find_head_end`는 머리 끝의 빈 줄을 찾는다. 아직 빈 줄까지 오지 않았으면 더 읽어야 한다고 알리고, 크기 제한을 넘으면 431을 알린다.
- `http_parse_headers`는 각 헤더 줄을 이름과 값으로 나눈다. 콜론이 없거나, 이름 문법이 틀렸거나, 접힌 줄이면 400이다. 헤더 개수를 넘으면 431이다. 이름과 값은 원본 바이트를 가리킨다.
- `http_header_get`은 이름으로 첫 헤더를 찾고, `http_header_count`는 같은 이름이 몇 개인지 센다. Host가 중복됐는지 검사할 때 개수 함수가 필요하다.
- `http_token_valid`는 메서드나 헤더 이름에 허용된 문자만 있는지 검사한다.
- `http_is_hop_by_hop`은 프록시가 다음 서버로 그대로 넘기지 말아야 할 헤더인지 검사한다. `Connection` 헤더가 추가로 지목한 이름도 확인한다.
- `http_headers_write`는 목록을 다시 `이름: 값\r\n` 줄로 만든다. 요청을 다른 서버에 전달할 때는 전달하면 안 되는 헤더를 뺄 수 있다.

### `common/http_framing.c`와 `.h` — 본문이 끝나는 위치 찾기

헤더를 다 읽어도 본문이 어디서 끝나는지 알아야 다음 요청과 섞이지 않는다. 이 파일은 헤더의 Content-Length나 Transfer-Encoding을 읽어 끝을 정한다.

- `lower_ascii`, `equals_ci`, `trim_ows_local`은 대소문자와 공백 차이를 무시하고 헤더 값을 비교하는 작은 도우미다.
- `parse_decimal`은 Content-Length 숫자를 읽는다. 숫자가 아니거나 너무 커서 정수에 들어가지 않으면 실패한다.
- `http_resolve_framing`은 Content-Length와 Transfer-Encoding을 함께 살펴 본문 방식을 고른다. 둘이 동시에 있거나 Content-Length 값들이 서로 다르면 거부한다. 응답은 HEAD 요청과 본문이 없는 상태 코드도 따로 고려한다.
- `http_body_tracker_init`은 본문 추적기의 시작 상태를 정한다.
- `hex_value`와 `trailer_tchar`는 chunked 본문의 16진수 길이와 끝부분에 붙는 헤더 줄을 검사하는 데 쓰인다.
- `http_body_track`은 이번에 새로 도착한 바이트 중 현재 본문에 속하는 양을 센다. 본문 뒤에 다음 요청이 붙어 있어도 그 바이트까지 현재 본문으로 삼지 않는다.
- `is_connection_token`과 `http_keep_alive`는 Connection 헤더를 읽어 응답 뒤 연결을 계속 쓸지 정한다. `close`가 있으면 닫고, HTTP/1.0은 `keep-alive`가 있어야 유지한다.

요청 파서는 chunked 요청을 거부하지만, 공용 본문 추적기는 chunked 응답 같은 스트림의 끝을 찾을 수 있다. 두 동작은 서로 모순되지 않는다. 공용 도구가 처리할 수 있는 형식과 요청 파서가 받아들이기로 정한 형식이 다르기 때문이다.

### `common/http_status.c`와 `.h` — 오류 응답의 기본 재료

- `http_reason`은 숫자 상태 코드에 붙일 짧은 이름을 돌려준다. 예를 들어 404에는 `Not Found`를 준다.
- `http_error_body`는 상태 코드와 이름을 넣은 간단한 HTML 본문을 버퍼에 만든다. Content-Type 헤더를 붙이는 일은 호출자가 한다.

### `downstream/listener.c`와 `.h` — 새 TCP 연결 받기

`listener`는 아직 요청을 처리하지 않는다. 서버가 연결을 기다리는 소켓을 준비하고, 연결 하나를 받을 뿐이다.

- `set_error`는 소켓 열기 과정 중 어느 단계에서 실패했는지 읽을 수 있는 문장으로 기록한다.
- `listener_open`은 주소와 포트에 소켓을 만들고 bind와 listen을 한다. 실패하면 만든 자원을 닫고 오류를 돌려준다.
- `listener_accept`는 대기 소켓에서 클라이언트 연결 하나를 받는다. 연결 소켓의 소유권은 호출자에게 간다. 보통 뒤이어 `conn_new`에 넘긴다.
- `listener_port`는 실제로 열린 포트를 조회한다. 포트 0으로 열었을 때 운영체제가 고른 번호를 알아내는 데 쓴다.
- `listener_close`는 대기 소켓을 닫는다. 이미 닫힌 것으로 표시된 음수 값은 건너뛴다.

### `downstream/request_parser.c`와 `.h` — 요청 머리 읽기

요청 파서는 바이트를 받아 요청 줄과 헤더를 검사한다. 본문 데이터를 읽거나 소켓에서 대기하지 않는다. 결과는 완성, 추가 입력 필요, 오류 셋 중 하나다.

- `lower_ascii`, `starts_http_scheme`는 `http://` 시작 여부를 대소문자 차이 없이 확인한다.
- `version_parse`는 HTTP 버전 모양을 확인하고, 문법은 맞지만 지원하지 않는 버전인지 구분한다.
- `initial_blank_bytes`는 요청 앞에 허용된 빈 줄이 있는지 센다.
- `first_line_too_long`은 요청 줄이 끝나기 전에 URI 길이 한도를 넘었는지 빨리 잡는다.
- `request_error`는 오류 상태 코드를 기록하고 파서 결과를 ERROR로 돌려주는 공통 처리다.
- `request_parse_head`는 메서드·버전·URI·헤더·Host·본문 길이 한도를 차례로 확인해 `http_request_t`를 채운다. 요청 본문은 나중에 `conn`이 받는다.

여기서 400은 문법 오류, 413은 본문 크기 초과, 414는 URI 길이 초과, 431은 머리나 헤더 개수 초과, 501은 지원하지 않는 메서드나 chunked 요청, 505는 지원하지 않는 HTTP 버전을 뜻한다.

### `downstream/uri.c`와 `.h` — 주소에서 경로 꺼내기

웹 주소의 경로와 query는 쓰임이 다르다. 경로는 라우팅에 쓰이고, query는 `?` 뒤의 추가 값이다.

- `lower_ascii`, `has_http_scheme`는 `http://`인지 대소문자 차이 없이 확인한다.
- `uri_split`은 대상을 경로와 query로 나누고, fragment(`#` 뒤)는 버린다. 이 단계에서는 `%20` 같은 표기를 디코딩하지 않는다.
- `uri_parse_absolute`는 `http://host/path`에서 host와 나머지 경로를 분리한다. 경로가 비어 있으면 `/`로 취급한다.
- `hex_value`는 `%XX`의 X를 숫자로 읽는다.
- `uri_decode_path`는 경로의 `%XX`를 한 번 풀어 바이트로 바꾼다. 잘못된 표기, NUL, 출력 버퍼를 넘는 결과는 거부한다. `+`는 공백으로 바꾸지 않는다.
- `path_normalize`는 중복 `/`와 `.`을 정리하고, `..`은 앞 경로 요소를 지운다. 최상위 `/` 위로 나가려는 경로는 거부한다.

순서는 중요하다. URI를 나눈 다음 경로만 디코딩하고 정리해야 query 문자열이 파일 경로처럼 바뀌지 않는다.

### `downstream/response_writer.c`와 `.h` — 응답을 바이트로 만들기

처리기가 만든 응답 계획은 아직 네트워크로 보낼 바이트가 아니다. 응답 작성기가 계획의 상태와 헤더를 HTTP 문장으로 바꾸고, 연결 처리기가 실제 전송을 맡는다.

- `status_has_no_body`는 특정 응답 상태가 본문을 보내지 않아야 하는지 확인한다.
- `response_write_head`는 상태 줄, 날짜, 서버 이름, 처리기가 추가한 헤더, Content-Length 또는 chunked 표시, 연결 유지 표시를 출력 버퍼에 쓴다.
- `response_write_chunk`는 본문 조각 앞에 16진수 길이를 붙이고 끝 표시를 붙인다.
- `response_write_last_chunk`는 chunked 본문이 끝났다는 표시를 쓴다.

여기서는 소켓으로 직접 쓰지 않는다. 버퍼에 바이트를 만들기만 하므로 부분 쓰기나 소켓 대기는 `conn`이 처리한다.

### `downstream/conn.c`와 `.h` — 연결 하나의 진행을 조정하기

`conn`은 여러 일을 직접 결정하기보다, 각 단계가 끝난 뒤 다음 단계를 고르는 조정자다. 한 연결의 현재 요청·응답, 버퍼, timeout, 소유 자원을 함께 관리한다.

#### 연결 안에 보관되는 것

- `fd`, `peer`, `client_ip`: 상대 소켓과 상대 주소, 로그에 쓸 IP를 담는다.
- `rbuf`: 클라이언트에서 받은 요청 머리·본문과 다음 요청 바이트를 담는다.
- `wbuf`: 만들었지만 아직 다 보내지 못한 응답 바이트를 담는다.
- `pipe_buf`: CGI가 출력한 응답 머리와 본문 앞부분을 임시 보관한다.
- `req`, `plan`, `job`: 현재 요청, 현재 응답 계획, 프록시 재시도 상태를 보관한다.
- `phase`, `deadline_ms`, `request_count`: 읽는 중인지 쓰는 중인지, 언제 timeout인지, 이 연결에서 몇 요청을 처리했는지 기억한다.
- `body_pos`, `file_off`, `response_bytes`: 메모리·파일 본문을 어디까지 보냈는지와 로그에 남길 전송량을 추적한다.
- `force_close`, `drain_after_write`, `plan_ready`, `body_deadline_set`, `header_deadline_set`: 오류 뒤 연결을 닫을지, 입력을 비울지, 계획 초기화가 끝났는지, 마감 시각을 이미 계산했는지 기억한다.
- `upstream_keep_alive`: 업스트림 연결을 재사용할 수 있는지 기록한다.
- CGI pipe와 업스트림 연결은 응답 계획이 소유한다. `conn_free`와 계획 정리 함수가 연결 종료 때 회수한다.

`conn_env_t`는 각 연결이 같이 보는 서버 설정·요청 한도·라우터·이벤트 엔진 포인터와 blocking 선택을 담는다. `conn_status_t`는 다음에 클라이언트를 읽을지 쓸지, CGI·업스트림 같은 다른 fd를 기다릴지, 연결을 닫을지 호출자에게 돌려준다.

#### 작은 도우미 함수

- `add_timeout`은 현재 시각과 제한 시간을 더해 마감 시각을 만든다.
- `input_limit`은 수신 버퍼가 담을 수 있는 요청 데이터 상한을 계산한다.
- `save_client_ip`는 상대 주소를 로그와 처리기에서 쓰기 쉬운 문자열로 바꾼다.
- `clear_request_state`는 끝난 요청의 자원을 정리하고 다음 요청을 받을 상태로 돌린다.
- `set_error_plan`은 상태 코드에 맞는 오류 응답을 준비하고 연결을 닫도록 표시한다.
- `wait_fd`는 읽기나 쓰기가 가능해질 때까지 제한 시간 안에서 기다린다.
- `send_all_client`는 일부만 전송되는 상황을 처리해 지정한 바이트를 모두 클라이언트로 보낸다.
- `set_fd_nonblock`은 pipe 같은 fd가 멈춰 기다리지 않도록 non-blocking 설정을 켠다.

#### CGI와 프록시 처리 함수

- `poll_cgi_fds`는 CGI 입력 pipe에 쓸 수 있는지, 출력 pipe에서 읽을 수 있는지 확인한다.
- `collect_cgi_head`는 CGI에 요청 본문을 보내면서 CGI 응답 머리를 받아 파싱한다.
- `proxy_exchange`는 프록시 요청을 backend에 보내고 응답 머리를 받는다. 실패하면 정책이 허용하는 경우 다른 backend를 시도한다.
- `dispatch_request`는 라우터 결과를 처리기에 전달해 응답 계획을 만든다. route가 없으면 404를 만든다. v2에서 아직 연결되지 않은 CGI·프록시 경로는 500으로 끝난다.
- `send_pipe_body`는 CGI 출력 본문을 끝까지 읽어 클라이언트에 보내고 CGI 자식을 정리한다.
- `send_upstream_body`는 업스트림 응답 본문을 경계 추적기가 끝났다고 할 때까지 전달한다.
- `send_body_blocking`은 본문 출처가 CGI pipe인지 업스트림인지 보고 맞는 전송 함수를 부른다.

#### 요청·응답 수명 함수

- `finish_request`는 접근 로그를 쓰고, 프록시 작업과 응답 계획을 정리하고, 다음 요청을 받을지 결정한다.
- `flush_response`는 응답 머리와 현재 지원하는 본문을 가능한 만큼 보내고 다음에 기다릴 이벤트를 돌려준다.
- `conn_new`는 연결 객체와 버퍼를 만들고 소켓 모드를 설정한다. 성공 뒤 fd 정리는 `conn`이 책임진다.
- `conn_free`는 연결이 가진 버퍼, 계획, 프록시 작업, 추가 fd, 클라이언트 소켓을 정리한다.
- `read_client_once`는 소켓에서 한 번 읽어 `rbuf`에 붙이고, 데이터 없음·상한 초과·EOF·오류를 구분한다.
- `conn_on_event`는 v2에서 이벤트 한 번을 처리한다. 읽기, 파싱, 처리, 응답 쓰기 중 지금 가능한 만큼만 진행하고 다음 대기 상태를 반환한다.
- `conn_on_timeout`은 현재 단계의 제한 시간이 끝났을 때 408 응답 또는 연결 종료를 선택한다.
- `conn_fd`와 `conn_deadline_ms`는 이벤트 엔진이 감시할 소켓과 다음 마감 시각을 조회하게 해준다.
- `conn_serve_blocking`은 v1에서 연결이 끝날 때까지 요청과 응답 처리를 반복한다.

`head_ready`, `parser_error`, `upstream_resp` 같은 필드는 소스 주석에서 미사용 또는 기록용으로 표시돼 있다. 이름만 보고 실제 제어에 쓰인다고 가정하지 않는다.

#### `conn`이 따르는 시간·종료 규칙

- 헤더 마감은 시작 시각에 제한 시간을 더해 한 번 정한다. 바이트가 조금씩 왔다고 마감을 뒤로 미루지 않는다.
- 본문은 머리 다음부터 필요한 길이만큼만 받는다. 같은 버퍼에 다음 요청이 있어도 이번 본문으로 소비하지 않는다.
- 응답 오류 뒤 즉시 닫으면 남은 입력 때문에 이미 보낸 응답이 유실될 수 있어, 쓰기 방향을 닫은 뒤 짧게 입력을 비운다.
- 클라이언트가 중계나 송신 중 끊으면 CGI 자식과 업스트림 연결을 계속 남겨두지 않고 회수한다.

## 추가 참고: 수신 버퍼와 요청 구조체의 메모리 관계

요청 파서가 만든 구조체가 모든 값을 새로 복사해 담는 것은 아니다. `str_t` 필드는 원본 수신 버퍼의 일부를 가리키고, 라우팅용 `path` 배열은 구조체 안에 직접 저장한다. 이 구분을 기억하면 요청 처리가 끝나기 전에 버퍼를 비우거나 늘리면 왜 안 되는지 이해할 수 있다.

```text
클라이언트에서 받은 바이트
┌─────────────────────────────────────────────────────────────────────┐
│ 요청 줄 │ 헤더 줄들 │ 빈 줄 │ 요청 본문 │ 다음 요청 바이트(있을 수 있음) │
└─────────────────────────────────────────────────────────────────────┘
                         conn.rbuf가 보관
       │                     │                      │
       └───────────────┬─────┴──────────────────────┘
                       ▼
http_request_t의 str_t 필드: method_raw, target, raw_path, query, host,
                            headers의 name/value, 수신 완료 뒤의 body
                            → conn.rbuf 안의 바이트를 빌려 가리킴

http_request_t.path: 디코딩·정규화한 경로를 구조체 내부 배열에 저장
                     → http_request_t가 직접 소유
```

- `conn.rbuf`는 요청 문자열과 본문을 포함한 바이트를 소유한다. `http_request_t`의 문자열 필드는 그 바이트의 포인터와 길이를 빌린다.
- `conn.c`는 요청 뷰가 살아 있는 동안 `rbuf`를 소비하거나 재할당하지 않는다고 주석에 적고 있다. 응답 처리가 끝나면 요청 바이트를 소비하고 다음 요청을 준비한다.
- `path`에는 `%XX` 디코딩과 경로 정규화 결과가 들어간다. 구조체가 고정 크기 배열을 쓰는 이유는 소스 주석에 따로 설명되어 있지 않으므로 설계 의도는 미확인이다.
- `body`도 요청 머리 파싱 때 채워지는 값이 아니다. `conn`이 본문 길이만큼 받은 뒤 수신 버퍼의 해당 구간을 가리키게 한다.

이 도식은 메모리 주소와 실제 바이트 오프셋을 그린 그림이 아니라, 소유(ownership)와 빌림(borrow)의 관계를 나타낸 설명도다. 확인 근거는 `src/common/types.h`의 `http_request_t` 정의와 `src/downstream/conn.c`의 연결 필드·버퍼 수명 처리다.

## 추가 참고: 연결 상태가 바뀌는 순서

`conn` 안의 처리 단계(`conn_phase_t`)와 엔진에 돌려주는 대기 상태(`conn_status_t`)는 서로 다른 값이다. 앞의 값은 읽기·쓰기·종료 중 어디에 있는지 나타내고, 뒤의 값은 호출자에게 다음에 무엇을 기다릴지 알려준다.

```text
[CONN_READING]
  ├─ 머리·본문 미완성 ──> CONN_WANT_READ ──(다음 이벤트)──────────┐
  │                                                             └─> [CONN_READING]
  ├─ 요청 완성 ──> route/handler ──> response_plan ──────────────┐
  └─ 입력 오류 ──> 오류 response_plan ──────────────────────────┤
                                                                  ▼
                                                           [CONN_WRITING]
                                                             ├─ 송신 중 막힘
                                                             │    └─> CONN_WANT_WRITE
                                                             │         └─(다음 이벤트)─> [CONN_WRITING]
                                                             ├─ 응답 완료 + keep-alive
                                                             │    └─> 요청 상태 정리 ──> [CONN_READING]
                                                             └─ close 조건·송신 오류
                                                                  └─> [CONN_FINISHED]
                                                                       └─> CONN_CLOSE
```

엔진 대기 값의 뜻은 다음과 같다.

| 반환 상태 | 다음에 할 일 | 소스에서 확인한 역할 |
| --- | --- | --- |
| `CONN_WANT_READ` | 클라이언트 소켓에 읽을 바이트가 생길 때 다시 호출한다. | 요청 바이트가 더 필요하거나, keep-alive 뒤 다음 요청을 기다린다. |
| `CONN_WANT_WRITE` | 클라이언트 소켓이 쓸 수 있을 때 다시 호출한다. | 응답 송신 버퍼에 아직 남은 바이트가 있다. |
| `CONN_WAIT_FD` | pipe·업스트림처럼 클라이언트 소켓이 아닌 fd 이벤트를 기다린다. | 공개 상태 열거형과 헤더 설명에는 있다. 현재 `conn.c`에서 이 값을 반환하는 경로는 확인되지 않았다. |
| `CONN_CLOSE` | 연결을 끝내고 호출자가 `conn_free`를 부른다. | 처리할 수 없는 입력·I/O 실패·종료 정책에 따라 연결을 닫는다. |

마감 시간은 현재 단계에 따라 다른 결과를 낸다. 머리나 본문을 받던 중 입력 바이트가 있으면 408 응답을 준비한 뒤 닫고, 요청 사이에 입력이 없는 유휴 연결은 응답 없이 닫는다. 이미 응답을 보내는 중 시간이 끝나면 새 오류 응답을 덧붙이지 않고 종료한다. CGI 실행이나 업스트림 응답 대기 시간 초과는 v1 경로에서 504로 처리하도록 주석에 적혀 있다.

위 흐름은 `src/downstream/conn.c`의 `conn_on_event`, `flush_response`, `conn_on_timeout`과 `src/downstream/conn.h`의 상태 정의를 연결해 적었다. 화살표는 소스에서 확인한 정상·오류 전이만 표시했다.

## 추가 참고: v1 blocking과 v2 이벤트 경로 비교

두 경로는 요청을 파싱하고 응답 계획을 실행한다는 큰 순서는 공유하지만, 연결을 진행시키는 방식과 현재 연결된 본문 종류가 다르다.

| 비교 항목 | v1 blocking 경로 | v2 이벤트 경로 |
| --- | --- | --- |
| 진입 함수 | `conn_serve_blocking` | `conn_on_event`, `conn_on_timeout` |
| 소켓 설정 | blocking 모드와 짧은 커널 I/O timeout을 설정한다. | non-blocking 모드로 설정한다. |
| 진행 방식 | `conn_serve_blocking`이 연결이 끝날 때까지 반복한다. 현재 단계에 맞춰 `poll`하고 공통 이벤트 처리 함수를 호출한다. | 이벤트가 왔을 때 할 수 있는 만큼 진행하고, `CONN_WANT_READ`·`CONN_WANT_WRITE` 같은 다음 상태를 호출자에게 돌려준다. |
| 현재 연결된 응답 본문 | 메모리, 파일, CGI pipe, 업스트림 응답 본문 경로가 연결되어 있다. | 메모리·파일 응답은 처리한다. CGI와 프록시 비동기 fd 처리는 아직 연결되지 않아 해당 경로가 500으로 끝난다. |
| 호출자·스레드 배치 | 연결이 끝날 때까지 호출이 머문다. 어느 worker가 연결 하나를 맡는지는 이 두 파일만으로 판단할 수 없다. | 이벤트 엔진이 다음 fd 이벤트를 전달한다. 이벤트 엔진의 스레드·워커 구성은 이 문서 범위 밖이다. |

따라서 “blocking”은 매번 `read`나 `write`가 끝없이 멈춘다는 뜻이 아니다. v1은 연결 처리를 한 호출 안에서 끝날 때까지 이어가며, `poll`과 마감 시간으로 기다림을 관리한다. v2는 처리 단계를 여러 이벤트 호출로 나눠 반환한다.

## 추가 참고: 오류 상태 코드 빠른 찾아보기

이 표는 `common`과 `downstream` 소스에서 생성 조건을 확인할 수 있는 경로를 모은다. `http_status.c`는 숫자에 대응하는 사유 문구를 제공하는 파일이지, 그 상태가 어떤 조건에서 발생하는지를 단독으로 정하는 파일은 아니다.

| 상태 | 의미 | 이 범위에서 확인한 발생 조건 | 확인 위치 |
| --- | --- | --- | --- |
| 400 | Bad Request | 요청 줄·헤더 문법 오류, HTTP/1.1 Host 누락·중복, 본문 경계 헤더의 모순 | `request_parse_head`, `http_parse_headers`, `http_resolve_framing` |
| 404 | Not Found | `router_match`가 route를 찾지 못함 | `dispatch_request` |
| 408 | Request Timeout | 머리나 본문을 받는 중 마감 초과. 요청 사이에 받은 바이트가 없는 유휴 timeout은 408을 보내지 않고 닫음 | `conn_on_timeout` |
| 413 | Content Too Large | 선언된 요청 본문 길이가 `max_body`를 넘음 | `request_parse_head` |
| 414 | URI Too Long | 요청 대상 길이가 `max_uri`를 넘음 | `request_parse_head` |
| 431 | Request Header Fields Too Large | 머리 크기 또는 헤더 개수 제한 초과 | `http_find_head_end`, `http_parse_headers` |
| 500 | Internal Server Error | v2에서 CGI·프록시 비동기 경로가 아직 연결되지 않은 경우, 또는 처리기가 유효하지 않은 응답 상태를 준 경우 | `dispatch_request` |
| 501 | Not Implemented | 지원하지 않는 메서드·요청 대상 형식, 또는 chunked 요청 본문 | `request_parse_head` |
| 502 | Bad Gateway | 잘못된 업스트림 응답 framing, CGI 응답 머리 오류, 프록시 교환 실패의 일부 경로 | `http_resolve_framing`, `collect_cgi_head`, `proxy_exchange` |
| 504 | Gateway Timeout | v1의 CGI 실행 또는 업스트림 응답 대기 마감 초과 | `conn.h` 처리 설명, `collect_cgi_head` |
| 505 | HTTP Version Not Supported | 문법상 유효하지만 지원하지 않는 HTTP 버전 | `request_parse_head` |

403·405·503은 상태 문구가 `http_status.c`에 있지만, 제안된 정적 파일·프록시 조건은 handler·upstream 구현에 있다. 그 구현은 이번 `common`·`downstream` 범위에서 확인하지 않았으므로 여기서는 실행 조건으로 단정하지 않는다. `conn.h`는 프록시 실패가 502·503·504 중 하나로 끝날 수 있다고 설명하지만, 구체적인 재시도 후 상태 선택은 upstream 쪽 정책이다.

## 추가 참고: 테스트 계획을 문서 흐름에 연결하기

각 README의 ID는 실행 결과가 아니라 테스트 계획의 분류다. README는 ID 묶음과 범위를 기록하지만, 모든 ID의 개별 시나리오 이름을 제공하지는 않는다. 아래 표는 문서에서 확인할 수 있는 수준까지만 연결했다.

| 학습 주제 | README·헤더 주석에 기록된 ID | 이 ID로 말할 수 있는 범위 |
| --- | --- | --- |
| 공용 헤더·본문 framing·오류 규칙 | `common/README.md`: 현재 기능 `E-ER-06`, `E-ER-08`, `E-ER-13`, `E-ER-14`, `E-KA-03~05`, `E-PX-03`, `E-PX-05`; 계약 최소셋 `U-COM-01`, `02`, `04`, `07`, `10`, `18`, `21`, `26`, `29`, `32`, `38`, `40` | common README가 현재 기능·계약 최소셋으로 분류한 ID다. 개별 ID가 어떤 입력 사례인지까지는 그 README에서 확인되지 않는다. |
| 연결 오류·keep-alive·소켓 종료 | `downstream/README.md`: `E-ER-01~14`, `E-KA-01~07`, `E-SL-01~04`; `conn_on_timeout` 주석은 `E-ER-10`, `E-ER-11`, `E-KA-06`, `E-SL-01`, `E-CG-07`, `E-PX-10`을 직접 연결 | timeout 함수 주석에 나열된 ID는 그 함수와 연결되어 있다. 나머지 ID는 디렉토리 테스트 범위 묶음이다. |
| URI 파싱·정규화 | `downstream/README.md`: 계약 최소셋 `U-DS-01`, `06`, `07`, `12`, `22`, `27`, `28`, `30`, `36`, `40`, `44`; 나머지 `U-DS-01~54`는 추후 범위로 표기 | README에는 URI 기능과 각 `U-DS` 번호를 일대일로 설명하는 표가 없다. `U-DS-06`, `U-DS-07`의 개별 시나리오는 ID만 보고 단정하지 않는다. |
| 이벤트 처리 API | `conn_on_event`: `U-DS-40`, `U-DS-44`, 추후 `U-DS-41~53`; `conn_on_timeout`: 위 오류·keep-alive 목록과 추후 `U-DS-47`, `U-DS-48` | `conn.h`의 함수별 주석에 직접 적힌 연결이다. |

이 ID 목록만으로 테스트가 실행됐거나 통과했다고 말할 수는 없다. 현재 작성 작업에서는 빌드와 테스트를 실행하지 않았다. 세부 시나리오를 ID에 붙이려면 해당 테스트 정의나 fixture가 추가로 필요하다.

## 읽기 전 기억할 점

- 위 내용은 제공된 `common`·`downstream` 소스 파일의 주석을 이해하기 쉬운 말로 정리한 것이다. 모든 C 주석을 원문 형태로 복사한 부록은 두지 않는다.
- `router`, `handler`, `upstream`, `engine`은 `conn`이 호출하는 경계까지만 설명했다. 그 내부 규칙은 이 문서에서 추측하지 않는다.
- 예시는 실행 결과가 아니다. 빌드, 테스트, 실제 요청 전송은 아직 확인하지 않았다.
