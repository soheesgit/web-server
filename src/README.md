# `common`·`downstream` 처음 읽는 사람을 위한 안내

이 문서는 `src/common/`과 `src/downstream/` 코드를 처음 보는 사람이 요청 하나를 따라가며 구조를 이해하도록 설명한다. 전체 서버의 모든 영역을 설명하는 문서는 아니다. 라우터, 처리기, 업스트림 구현, 실행 엔진의 내부 동작은 범위 밖이다.

먼저 아래 요청 예시를 따라 읽는다. 그다음 표를 써서 낯선 타입이나 함수 이름을 다시 찾는다. 표만 읽고 구현 흐름을 추측할 필요는 없다.

## 요청 하나가 처리되는 큰 흐름

```text
클라이언트
  → listener가 TCP 연결을 받음
  → conn이 연결 버퍼와 마감 시각을 관리함
  → 요청 바이트를 모음
  → request_parse_head가 요청 줄과 헤더를 검사함
  → conn이 요청 본문을 받음
  → router와 handler가 응답 계획을 준비함
  → response_writer가 응답 상태 줄과 헤더를 바이트로 만듦
  → conn이 메모리·파일·CGI·업스트림 본문을 전송함
  → 연결을 닫거나 다음 요청을 기다림
```

1. `listener_open`은 주소와 포트에 TCP 대기 소켓을 연다. `listener_accept`는 연결 하나를 받아 연결 소켓(fd)을 돌려준다.
2. `conn_new`는 클라이언트 연결을 나타내는 `conn_t`를 만든다. 연결 환경에 따라 blocking 방식(v1) 또는 non-blocking 방식(v2)을 설정한다.
3. `conn`은 읽은 바이트를 수신 버퍼에 모은다. TCP는 메시지 단위가 아니라 바이트 흐름이므로 요청 줄이나 헤더가 여러 번 나뉘어 도착할 수 있다. 반대로 한 번 읽을 때 요청 둘이 붙어 올 수도 있다.
4. `request_parse_head`는 첫 요청의 머리까지만 파싱한다. 아직 덜 왔으면 `HTTP_PARSE_INCOMPLETE`, 형식 오류면 `HTTP_PARSE_ERROR`, 완성됐으면 `HTTP_PARSE_DONE`을 돌려준다. 다음 요청이나 본문까지 한꺼번에 파싱하지 않는다.
5. 요청 머리가 완성되면 `conn`은 `Content-Length`에 적힌 본문 바이트를 모은다. 본문을 다 받기 전에는 처리기를 부르지 않는다. 요청의 chunked 본문은 이 구현에서 상태 501로 거부한다.
6. `conn`은 요청의 host와 정규화된 path를 라우터에 전달하고, 라우팅 결과를 처리기에 넘긴다. 라우터와 처리기 자체의 구현은 이 문서 범위에 포함되지 않는다.
7. 처리기는 보낼 내용의 계획인 `response_plan_t`를 준비한다. 본문은 메모리, 파일, CGI pipe, 업스트림 연결 중 하나에서 올 수 있다.
8. `response_write_head`가 상태 줄과 헤더를 출력 버퍼에 쓴다. 이후 `conn`이 계획의 본문을 읽어 클라이언트에 보낸다.
9. 응답 뒤에는 요청의 keep-alive 여부, 응답의 close 표시, 오류 상태, 최대 요청 수를 보고 연결을 유지하거나 닫는다. 연결을 유지하면 이번 요청이 사용한 바이트만 버퍼에서 지우고 남은 바이트로 다음 요청을 처리한다.

응답 머리를 보낸 뒤 본문 전송이 실패하면 새 오류 응답을 보낼 수 없다. 이미 클라이언트가 응답을 받기 시작했기 때문에 연결을 닫아 실패를 알린다.

## 예시 요청 하나를 코드 흐름으로 따라가기

아래는 설명을 위한 가상 입력이다. 실제 서버에 보냈거나 테스트에서 관측한 결과가 아니다. 한 요청이 코드의 어느 부분을 거치는지 보여주기 위한 예시다.

```http
POST /docs/./intro%20page?lang=ko HTTP/1.1
Host: example.test
Content-Length: 4

DATA
```

### 1. 연결을 받고 바이트를 모은다

`listener_open`은 서버가 기다릴 TCP 소켓을 만든다. `listener_accept`가 클라이언트 하나를 받아 fd를 돌려주면, `conn_new`가 그 fd를 소유하는 `conn_t`를 만든다. 이때 v1은 timeout이 있는 blocking 방식, v2는 non-blocking 방식을 사용하도록 설정된다.

`conn`은 클라이언트에서 읽은 바이트를 `rbuf`에 모은다. TCP는 HTTP 요청 단위로 데이터를 전달하지 않는다. 위 요청이 요청 줄·헤더·본문 세 번으로 나뉘어 올 수도 있고, 다음 요청의 일부가 `DATA` 뒤에 함께 올 수도 있다. 그래서 한 번의 `read`가 곧 한 요청이라고 가정하지 않는다.

`conn_t`는 연결의 작은 작업 공간이다. `rbuf`에는 받은 요청 바이트, `wbuf`에는 아직 보내지 못한 응답 바이트가 있다. 현재 요청은 `req`, 현재 응답 계획은 `plan`, 프록시 재시도 상태는 `job`에 둔다. 연결의 현재 단계와 다음 timeout도 함께 들고 있어, 이벤트가 오면 `conn`이 어디서 이어서 처리할지 알 수 있다.

### 2. 요청 머리와 본문을 분리한다

빈 줄은 요청 머리의 끝이다. 예시에서는 `Content-Length: 4` 다음의 빈 줄까지가 머리이고, 그 뒤 네 바이트 `DATA`가 본문이다.

`conn`은 `request_parse_head`를 호출한다. 이 함수는 머리 끝을 찾을 때 `http_find_head_end`를 쓰고, 헤더 줄을 나눌 때 `http_parse_headers`를 쓴다. 요청이 덜 도착했다면 파서는 오류를 만들지 않고 `HTTP_PARSE_INCOMPLETE`를 돌려준다. `conn`은 다음 입력을 읽은 뒤 다시 파싱한다. 형식이 틀렸다면 `HTTP_PARSE_ERROR`와 응답 상태 코드를 돌려준다.

완성되면 파서는 첫 요청만 `http_request_t`에 담는다. 다음 요청 바이트가 수신 버퍼에 이미 있어도 `head_len`은 첫 요청 머리의 끝을 가리킨다. 요청 안의 `str_t` 값은 문자열 사본이 아니라 `rbuf`의 일부를 가리키므로, 요청 처리가 끝나기 전에 버퍼를 움직이거나 다시 할당하면 안 된다.

파서 결과의 세 상태는 서로 다른 뜻이다. `DONE`은 이 요청 머리가 준비됐다는 뜻이고, `INCOMPLETE`는 잘못된 입력이 아니라 바이트를 더 받아야 한다는 뜻이며, `ERROR`는 입력을 더 받아도 해결되지 않는 규칙 위반이다. 일반적인 오류 상태는 잘못된 문법 400, 본문 한도 초과 413, 대상 URI 한도 초과 414, 머리나 헤더 수 한도 초과 431, 지원하지 않는 메서드나 chunked 요청 501, 지원하지 않는 HTTP 버전 505다.

### 3. 대상 주소를 라우팅에 쓸 형태로 바꾼다

예시의 메서드는 `POST`, 대상은 `/docs/./intro%20page?lang=ko`, 버전은 HTTP/1.1이다. 파서는 메서드와 버전을 확인한 뒤 대상 처리에 `uri.c`의 함수를 사용한다.

`uri_split`은 경로와 query를 가른다. 이 예시에서는 경로가 `/docs/./intro%20page`, query가 `lang=ko`다. `uri_decode_path`가 `%20`을 공백으로 바꾸고, `path_normalize`가 `.` 경로 요소를 제거한다. 따라서 라우터에 넘길 path는 `/docs/intro page`가 된다. query는 별도 값으로 유지된다. 프록시가 원본 경로 표기를 필요로 할 수 있어 요청 구조체에는 정규화 경로와 원본 경로를 따로 둔다.

HTTP/1.1의 origin-form 요청에는 Host 헤더가 하나 필요하다. 파서는 헤더 목록에서 Host를 확인하고 `http_request_t`에 host를 채운다. 여기서 문서가 설명하는 범위는 이 값이 `conn`을 통해 라우터에 넘어가는 지점까지다. 어떤 route가 선택되고 그 route가 무슨 응답을 만드는지는 라우터·처리기 영역의 책임이다.

### 4. 본문 길이를 정하고 요청 처리를 시작한다

`http_resolve_framing`은 `Content-Length: 4`를 보고 본문 방식이 `FRAMING_LENGTH`, 길이가 4라고 기록한다. `conn`은 이 네 바이트가 모일 때까지 본문 timeout을 적용해 읽는다. 네 바이트가 다 모이면 `req.body`가 그 구간을 가리키고, 그제야 요청을 라우터와 처리기에 넘긴다.

요청 파서는 현재 chunked 요청을 받아들이지 않고 501로 거부한다. 공용 `http_body_track`이 chunked 형식도 추적할 수 있다는 사실과 혼동하지 않는다. 그 추적기는 업스트림 응답처럼 바이트 조각을 전달하면서 본문 끝을 찾아야 하는 곳에서 쓰인다.

길이 방식은 “본문이 4바이트에서 끝난다”처럼 끝 위치를 Content-Length로 바로 안다. chunked 방식은 각 조각 앞의 16진수 길이를 따라가야 한다. 예를 들어 `4\r\nDATA\r\n0\r\n\r\n`은 4바이트 데이터 조각 뒤에 끝 조각이 오는 모양이다. `http_body_track`은 여러 번 나눠 들어온 이 조각들을 추적하고, 본문 뒤에 붙은 다음 메시지 바이트는 현재 본문에 포함하지 않는다.

### 5. 처리 결과를 응답 계획으로 받고 바이트를 보낸다

`conn`은 `router_match(host, path)`로 경로에 맞는 route를 찾고, `handler_dispatch`에 요청을 전달한다. 맞는 route가 없으면 `conn`은 404 응답 계획을 만든다. route가 있으면 처리기가 `response_plan_t`를 채운다. 이 계획에는 상태 코드와 헤더, 본문이 메모리·파일·CGI pipe·업스트림 중 어디에서 오는지가 들어간다.

`response_plan_t`는 응답을 직접 보내는 함수가 아니라 전송할 내용을 설명하는 묶음이다. `head.status`와 `head.fields`에 상태와 추가 헤더를 담고, `kind`가 본문 출처를 고른다. `BODY_MEM`이면 `body.mem.data`가 바이트를 갖고, `BODY_FILE`이면 fd·시작 위치·길이를 갖는다. `BODY_PIPE`는 CGI pipe와 자식 프로세스를, `BODY_UPSTREAM`은 프록시 대상 연결과 본문 추적 상태를 가진다. 계획은 그 자원들의 소유자이기도 해서 응답 뒤 `plan_cleanup`이 회수한다. `conn`이 계획을 실행하는 역할과 처리기가 계획을 만드는 역할을 나누는 이유가 여기에 있다.

설명만을 위해 처리기가 상태 200과 메모리 본문 `OK`를 계획했다고 가정해 보자. 이것은 실제 처리기 결과를 확인한 것이 아니다. `response_write_head`는 계획에서 상태와 헤더를 읽어 응답 머리 바이트를 만든다. 이 함수가 만드는 상태 줄은 `HTTP/1.1` 형식이며, 필요한 날짜·서버·본문 길이·연결 헤더를 붙인다. 그다음 `conn`이 계획에 적힌 본문 출처에서 바이트를 읽어 클라이언트에 보낸다.

본문 출처에 따라 실제 전송 방법은 다르다. 메모리는 버퍼에서 복사하고, 파일은 지정된 구간을 보내고, CGI pipe와 업스트림 응답은 읽은 조각을 계속 중계한다. chunked로 보낼 때는 `response_write_chunk`로 각 조각을 감싸고 끝에 `response_write_last_chunk`를 쓴다.

### 6. 연결을 재사용하거나 자원을 정리한다

응답이 끝나면 `conn`은 요청의 keep-alive, 응답 계획의 close 표시, 처리한 요청 수를 보고 소켓을 유지할지 결정한다. HTTP/1.1은 `Connection: close`가 없으면 보통 유지하고, HTTP/1.0은 `keep-alive`를 요청했을 때 유지한다. 유지할 경우 이번 요청의 머리와 본문 바이트만 `rbuf`에서 소비한다. 뒤에 다음 요청이 남아 있으면 별도의 새 연결 없이 바로 다시 파싱한다.

처리가 끝나면 프록시 작업과 응답 계획의 자원을 정리한다. `response_plan_t`가 파일 fd, CGI 자식 프로세스, 업스트림 연결을 소유할 수 있으므로 정리는 단순히 구조체 메모리를 비우는 일이 아니다. 각 자원을 닫거나 회수해야 한다.

### 중간에 실패하면 어떻게 되나

- 요청 머리가 아직 도착 중이면 연결은 기다린다. 머리 형식이 잘못됐거나 크기 제한을 넘으면 해당 오류 상태로 응답하고 연결을 닫는다.
- 헤더·본문 마감이 지나면 timeout 경로로 간다. 헤더나 본문 수신 중 timeout은 408이다. 요청 사이에 아무 입력 없이 idle timeout이 나면 응답 없이 닫는다.
- 라우트가 없으면 404 응답 계획을 만든다. 프록시 실패는 실패 이유와 재시도 정책에 따라 다시 시도하거나 502·503·504 응답 계획으로 끝난다.
- 클라이언트 응답 머리를 이미 보낸 뒤 CGI·파일·업스트림 본문 전송이 실패하면 별도 오류 응답을 붙일 수 없다. 연결을 닫고, 필요한 자원을 회수한다.
- 클라이언트가 처리 중 연결을 끊으면 `conn`은 CGI 자식과 업스트림 연결 같은 자원을 정리한다.

이 흐름은 `conn.h`의 처리 순서 주석과 `conn.c`의 연결 상태 구현에 적혀 있다. 단, 위의 `OK` 응답은 이해를 위한 가상 예시이며 테스트 통과나 실서버 관측을 뜻하지 않는다.

## 다시 찾아볼 낱말

앞의 흐름을 읽다가 낯선 단어가 나오면 아래 표에서 뜻을 확인한다. 표는 흐름을 대신하는 설명이 아니라, 읽다가 막힌 용어를 찾아보는 용도다.

| 낱말 | 이 코드에서 뜻하는 것 |
| --- | --- |
| 요청(request) | 클라이언트가 보내는 시작 줄, 헤더, 선택적인 본문. 예: `GET /hello HTTP/1.1` |
| 응답(response) | 서버가 보내는 상태 줄, 헤더, 선택적인 본문. 예: `HTTP/1.1 200 OK` |
| 헤더(header) | `Host: example.test`처럼 요청이나 응답의 부가 정보를 담는 이름과 값 |
| 머리(head) | 본문 앞부분. 요청 줄이나 상태 줄, 헤더, 마지막 빈 줄까지를 가리킨다 |
| 소켓(socket) | TCP 연결을 통해 상대와 바이트를 주고받는 운영체제 자원 |
| fd(file descriptor) | 프로세스가 소켓, 파일, pipe 같은 자원을 가리킬 때 쓰는 정수 번호 |
| 버퍼(buffer) | 아직 처리하거나 보내지 않은 바이트를 임시 보관하는 메모리 |
| 파싱(parse) | 받은 바이트를 요청·헤더 같은 구조로 나누고 규칙을 검사하는 일 |
| 직렬화(serialize) | 구조체의 값을 HTTP가 정한 바이트 순서로 만들어 내는 일 |
| 본문 경계(framing) | 본문이 몇 바이트인지, 청크 형식인지, 연결 종료까지인지 정하는 규칙 |
| chunked | 본문을 여러 조각으로 보내며 각 조각 앞에 16진수 길이를 붙이는 방식. 길이 0인 조각이 끝을 나타낸다 |
| hop-by-hop 헤더 | 현재 연결에만 적용되어 프록시가 다음 서버로 그대로 넘기면 안 되는 헤더 |
| origin-form / absolute-form | 요청 대상 표기 방식. `/path`로 시작하는 형식과 `http://host/path`처럼 scheme(통신 방식 이름)과 host까지 포함한 형식 |
| 빌림(borrow) | 구조체가 바이트를 복사하지 않고 다른 버퍼의 일부를 가리키는 것. 원본 버퍼가 바뀌거나 해제되면 그 포인터도 더 쓸 수 없다. |
| 계획(plan) | 응답 내용을 만들기보다, 응답 머리와 본문을 어디서 가져올지 기록한 `response_plan_t` |
| 업스트림(upstream) | 프록시가 요청을 전달하는 뒤쪽 서버 |
| CGI | 별도 자식 프로세스를 실행해 응답을 받아오는 방식 |
| blocking / non-blocking | blocking 호출은 I/O가 진행될 때까지 기다리고, non-blocking 호출은 지금 할 수 있는 만큼 진행한 뒤 기다릴 이벤트를 돌려준다 |
| 라우터(router) | 요청의 host와 path를 보고 어느 처리기로 보낼지 고른다 |
| 처리기(handler) | 선택된 요청에 어떤 응답을 만들지 정해 `response_plan_t`에 기록한다 |
| 이벤트 엔진(engine) | non-blocking 연결에서 어떤 fd를 기다릴지 등록하고 이벤트를 전달한다. 내부 구현은 이 문서 범위 밖이다 |

## 두 디렉토리의 경계

| 디렉토리 | 맡은 일 | 하지 않는 일 |
| --- | --- | --- |
| [`common/`](common/README.md) | 요청과 응답이 함께 쓰는 HTTP 헤더, 본문 길이, 연결 유지 규칙과 경계 타입을 처리한다. | 소켓이나 파일을 읽고 쓰지 않는다. |
| [`downstream/`](downstream/README.md) | 클라이언트 소켓을 받아 요청을 읽고, 다른 영역에 처리를 맡기고, 응답을 전송한다. | 응답 내용 자체를 정하는 라우팅·처리기 정책을 소유하지 않는다. |

`common` 함수는 주어진 바이트와 구조체를 계산·변환한다. `downstream/conn.c`가 실제 I/O와 시간 제한, 자원 정리를 담당한다. 따라서 프로토콜 규칙을 볼 때는 `common`, 연결이 언제 읽고 쓰는지 볼 때는 `conn`부터 읽는다.

## 다시 찾아보는 공용 타입: `common/types.h`

### 값과 상태를 나타내는 열거형

| 타입 | 설명 |
| --- | --- |
| `http_method_t` | 요청 메서드. GET, HEAD, POST, 그 밖의 메서드를 구분한다. |
| `http_parse_result_t` | 파서가 완료됐는지, 입력을 더 기다려야 하는지, 오류인지 나타낸다. |
| `http_framing_kind_t` | 본문이 없음, 길이 지정, chunked, 연결 종료까지 중 어떤 규칙을 따르는지 나타낸다. |
| `http_body_result_t` | 본문 경계 추적이 더 필요함, 끝남, 형식 오류 중 무엇인지 나타낸다. |
| `body_kind_t` | 응답 본문이 없음, 메모리, 파일, CGI pipe, 업스트림 중 어디에 있는지 나타낸다. |
| `proxy_fail_t` | 프록시 시도에서 연결·송신·응답 대기·응답 형식 중 어디서 실패했는지 나타낸다. |
| `proxy_next_t` | 프록시 실패 뒤 다른 백엔드로 재시도할지, 오류 응답으로 끝낼지 나타낸다. |

### 요청·응답과 진행 상태를 담는 구조체

| 타입 | 담는 내용과 쓰임 |
| --- | --- |
| `http_header_t` | 헤더 한 개의 이름과 값. 값은 원본 수신 버퍼를 빌린다. |
| `http_headers_t` | 헤더 여러 개를 받은 순서대로 담는다. 같은 이름의 헤더도 합치지 않는다. |
| `http_framing_t` | 본문을 읽는 규칙과 길이를 담는다. |
| `http_limits_t` | 요청 머리, URI, 헤더 수, 본문에 적용할 상한을 전달한다. |
| `http_body_tracker_t` | 여러 조각으로 받은 본문에서 현재 위치와 끝을 추적한다. 본문 바이트를 복사하지 않는다. |
| `http_request_t` | 요청 메서드, 원래 대상, 정규화된 경로, query, 헤더, 본문 길이 규칙, 연결 유지 정보를 담는다. `body`는 머리 파서가 아니라 `conn`이 채운다. |
| `http_response_t` | 업스트림 응답의 상태 줄, 헤더, 본문 규칙, 연결 재사용 정보를 담는다. |
| `http_head_out_t` | 클라이언트에 보낼 상태 코드, 추가 헤더, 본문 규칙, 연결 종료 표시를 담는다. |
| `response_plan_t` | 응답 머리와 본문 출처를 묶는다. 파일 fd, CGI pipe와 자식, 업스트림 연결처럼 동적으로 소유한 자원은 `plan_cleanup`이 정리한다. |
| `proxy_job_t` | 프록시가 보낼 직렬화 요청, 대상 그룹과 현재 백엔드, 시도 수, 요청을 보냈는지 여부를 담는다. 그룹과 백엔드 포인터는 빌린다. |

수명 규칙이 중요한 이유: 요청의 `str_t` 필드는 수신 버퍼 내부를 가리킨다. `conn`이 요청 처리를 끝내기 전에 버퍼를 이동하거나 재할당하면 그 포인터가 깨질 수 있다. 반대로 `response_plan_t`는 여러 fd와 버퍼를 직접 소유하므로 응답이 끝날 때 정리해야 한다.

## 함수 이름을 다시 찾을 때: `common/` 파일과 공개 함수

아래 표는 다른 소스 파일에서도 부를 수 있는 공개 함수를 중심으로 정리한다. 각 `.c` 파일 안에서만 쓰는 `static` 보조 함수는 외부 호출 대상이 아니며, 함수 바로 위의 소스 주석에서 역할을 설명한다.

### `http_headers.h` / `http_headers.c`

헤더의 끝을 찾고, 헤더 줄을 파싱하고, 이름으로 검색하고, 전달할 헤더 줄을 출력한다.

| 함수 | 역할 |
| --- | --- |
| `http_find_head_end` | 입력 바이트에서 시작 줄과 헤더가 끝나는 빈 줄을 찾는다. 아직 덜 왔으면 추가 입력을 요청한다. |
| `http_parse_headers` | 헤더 영역을 이름·값 쌍으로 나눈다. 잘못된 줄이나 너무 많은 헤더는 오류로 처리한다. |
| `http_header_get` | 이름이 같은 첫 헤더를 대소문자 구분 없이 찾는다. |
| `http_header_count` | 이름이 같은 헤더가 몇 개인지 센다. Host 중복 검사 등에 쓰인다. |
| `http_token_valid` | 메서드나 헤더 이름처럼 token 문법을 따라야 하는 문자열을 검사한다. |
| `http_is_hop_by_hop` | 한 연결에만 적용되는 헤더인지 판정한다. 프록시가 헤더를 전달할 때 제거 여부를 정하는 데 쓰인다. |
| `http_headers_write` | 헤더 목록을 `Name: value\r\n` 모양으로 출력 버퍼에 복사한다. 선택하면 hop-by-hop 헤더를 뺀다. |

### `http_framing.h` / `http_framing.c`

헤더를 보고 본문을 어디까지 읽을지 정하고, 본문이 조각나 도착해도 경계를 추적한다.

| 함수 | 역할 |
| --- | --- |
| `http_resolve_framing` | Transfer-Encoding과 Content-Length를 검사해 본문 읽기 방식을 정한다. 둘이 함께 있거나 서로 다른 길이가 있으면 거부한다. 응답은 HEAD와 1xx·204·304 상태 규칙도 적용한다. |
| `http_body_tracker_init` | 추적기를 특정 본문 길이 방식으로 초기화한다. |
| `http_body_track` | 새 바이트 중 현재 본문에 속하는 양을 세고 끝을 찾는다. 다음 메시지에 속한 바이트는 사용하지 않는다. |
| `http_keep_alive` | HTTP 버전과 Connection 헤더를 보고 연결을 계속 쓸지 판단한다. `close`가 있으면 종료한다. |

### `http_status.h` / `http_status.c`

| 함수 | 역할 |
| --- | --- |
| `http_reason` | 숫자 상태 코드에 대응하는 사유 문구를 돌려준다. |
| `http_error_body` | 상태 코드와 사유 문구로 간단한 HTML 오류 본문을 출력 버퍼에 덧붙인다. Content-Type 헤더는 호출자가 추가한다. |

## 함수 이름을 다시 찾을 때: `downstream/` 파일과 공개 함수

### `listener.h` / `listener.c`

| 함수 | 역할 |
| --- | --- |
| `listener_open` | 주소와 포트에 TCP 대기 소켓을 만들고 listen 상태로 둔다. |
| `listener_accept` | 대기 중인 클라이언트 연결 하나를 받는다. |
| `listener_port` | 대기 소켓에 실제로 연결된 포트를 돌려준다. 포트 0으로 열었을 때 배정 포트를 알아내는 데 쓴다. |
| `listener_close` | 대기 소켓을 닫는다. |

### `request_parser.h` / `request_parser.c`

`request_parse_head`는 시작 줄과 헤더를 검사해 `http_request_t`를 만든다. 메서드, HTTP/1.0·1.1 버전, 대상 URI, Host 개수, 본문 크기 상한, keep-alive 규칙을 적용한다. 본문 데이터는 읽지 않는다. 더 많은 입력이 필요한 상황과 오류 응답 상태도 호출자에게 구분해 돌려준다.

### `uri.h` / `uri.c`

| 함수 | 역할 |
| --- | --- |
| `uri_split` | URI 대상을 경로와 query로 나눈다. 퍼센트 디코딩은 하지 않는다. |
| `uri_parse_absolute` | `http://host/path` 형태에서 authority와 나머지 경로를 나눈다. |
| `uri_decode_path` | 경로의 `%XX`를 한 번 디코딩한다. 잘못된 escape와 NUL 결과를 거부한다. |
| `path_normalize` | 연속 `/`, `.`, `..`를 정리하고 경로가 루트 위로 올라가는지 검사한다. |

요청 파서가 이 함수들을 차례로 부른다: 대상에서 authority·경로·query를 구분하고, 경로를 한 번 디코딩한 뒤 정규화한다. query는 경로 파일 이름처럼 정규화하지 않는다.

### `response_writer.h` / `response_writer.c`

| 함수 | 역할 |
| --- | --- |
| `response_write_head` | 상태 줄과 날짜, 서버 이름, 응답 헤더, 본문 길이 규칙, 연결 헤더를 출력 버퍼에 쓴다. |
| `response_write_chunk` | 본문 데이터 한 조각을 chunked 형식으로 출력한다. |
| `response_write_last_chunk` | chunked 본문 끝을 나타내는 `0\r\n\r\n`을 출력한다. |

### `conn.h` / `conn.c`

`conn_t`는 내부가 헤더에 드러나지 않는 연결 객체다. 내부 버퍼와 현재 요청·응답 계획, 마감 시각, 자원 소유권을 `conn.c`가 관리한다.

| 함수 | 역할 |
| --- | --- |
| `conn_new` | 소켓과 실행 환경을 받아 연결 상태를 만든다. 성공하면 소켓 fd 소유권은 `conn`으로 옮겨간다. |
| `conn_free` | 연결과 연결이 소유한 버퍼, 응답 자원, 프록시 작업, fd를 정리한다. |
| `conn_serve_blocking` | v1 방식으로 연결을 닫을 때까지 요청과 응답을 순서대로 처리한다. |
| `conn_on_event` | v2 방식으로 한 fd 이벤트에서 가능한 만큼만 진행하고 다음 대기 상태를 돌려준다. |
| `conn_on_timeout` | 현재 단계의 마감이 지난 경우 응답을 만들지, 연결을 닫을지 결정한다. |
| `conn_fd` | 연결의 클라이언트 소켓 fd를 조회한다. |
| `conn_deadline_ms` | 다음에 적용할 마감 시각을 조회한다. |

`conn_status_t`는 엔진이 클라이언트 읽기, 클라이언트 쓰기, 다른 fd 대기 중 무엇을 해야 하는지, 연결을 정리해야 하는지 나타낸다. `conn_env_t`는 모든 연결이 공유하는 설정, 요청 한도, 라우터, 이벤트 엔진 포인터를 제공한다.

## 현재 구현에서 주의할 범위

- 요청 본문은 Content-Length 방식만 받는다. 공용 `http_body_track`은 chunked 추적 기능도 제공하지만, 요청 파서는 chunked 요청을 501로 거부한다.
- v1 blocking 경로는 CGI pipe와 업스트림 프록시 응답 본문 중계를 연결한다.
- v2 이벤트 경로는 메모리·파일 응답을 처리한다. 비동기 CGI와 프록시 fd 진행은 아직 연결되지 않아 해당 요청에 500을 돌려준다.
- 오류 본문을 만들 때 상태 줄과 헤더를 먼저 보내고, 본문 소스가 파일·pipe·업스트림이면 `conn`이 그 소스에서 전송한다.
- 다른 영역의 실제 구현과 서버 전체 실행은 여기서 확인하지 않았다. 이 안내만으로 전체 서버가 실행된다고 판단하면 안 된다.

## 코드에서 확인한 내용과 아직 확인하지 않은 내용

**코드와 기존 디렉토리 문서에서 확인한 내용:** 함수 목적, 입력·출력 형태, 경계 타입 수명, 요청 처리 단계, v1과 v2의 CGI·프록시 차이.

**이번 문서 작업에서 확인하지 않은 내용:** 빌드 성공, 테스트 결과, 실제 네트워크에서의 요청·응답 동작. 실행 검증은 하지 않았다.

테스트 이름과 단계 목록은 각 디렉토리의 [`common/README.md`](common/README.md)와 [`downstream/README.md`](downstream/README.md)를 참고한다. README의 테스트 이름은 검증 계획이며, 이번 문서 작성에서 실행한 결과가 아니다.
