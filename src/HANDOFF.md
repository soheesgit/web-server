# `common`·`downstream` 1차 작업 인수인계

## 다음 작업자가 알아야 할 범위

프로젝트 원본에서 수정한 파일은 `src/` 안의 `common/`과 `downstream/`에 한정된다. 서버 전체를 완성하는 작업은 아니다. 라우터, 처리기, 업스트림 구현, 실행 엔진은 다음 영역과 연결되는 지점만 확인하고 내부 구현은 수정하지 않았다.

처음 보는 작업자는 먼저 [`README.md`](README.md)의 요청 예시를 따라가면 된다. 이 예시는 클라이언트가 보낸 바이트가 `conn`에서 요청 구조체가 되고, 라우터·처리기로 넘어간 다음 응답 계획과 전송으로 이어지는 과정을 설명한다. 뒤쪽의 표는 함수나 타입 이름을 다시 찾을 때 쓴다. 각 영역의 구현 단계와 계획된 테스트 ID는 [`common/README.md`](common/README.md)와 [`downstream/README.md`](downstream/README.md)에 있다.

## 1차 작업이 놓인 위치

`common`은 요청과 응답이 함께 쓰는 HTTP 규칙을 바이트 단위로 처리한다. `downstream`은 클라이언트 연결을 소유하고, 그 규칙을 써서 요청을 읽은 뒤 응답을 내보낸다. 그래서 이 작업의 중심 경로는 `listener`가 연결을 받고 → `conn`이 요청을 모으고 → 요청 파서와 공용 코드가 구조를 만들고 → 라우터·처리기에 넘기고 → `conn`과 응답 작성기가 결과를 전송하는 순서다.

여기서 `response_plan_t`는 처리기가 정한 응답과 본문 자원을 `conn`에 넘기는 경계다. `conn`은 그 계획을 실행하고 연결을 재사용할지 정리할지 판단한다. `common`의 파서는 본문을 읽거나 소켓에 쓰지 않는다. 이 구분이 섞이면 요청 파서에 I/O를 추가하거나 응답 자원 해제를 빠뜨릴 위험이 생기므로, 다음 작업도 두 영역의 책임을 유지해야 한다.

## 1차 작업에서 한 일

### 공용 HTTP 규칙 구현과 설명

- `src/common/http_headers.c`: 메시지 머리 끝 찾기, 헤더 줄 파싱, 헤더 조회·개수 계산, token 검사, hop-by-hop 판정, 헤더 출력.
- `src/common/http_framing.c`: Transfer-Encoding·Content-Length 기반 본문 방식 결정, 조각 단위 본문 끝 추적, keep-alive 판정.
- `src/common/http_status.c`: 상태 코드 사유 문구와 간단한 HTML 오류 본문 출력.
- `src/common/types.h`: 요청, 응답, 본문 추적, 응답 계획, 프록시 작업에 쓰는 경계 타입과 수명 설명. 이어서 각 타입에 초보자용 `역할:` 한 줄을 추가했다.

### 클라이언트 연결 경로 구현과 설명

- `src/downstream/request_parser.c`: 요청 머리 파싱, 메서드·버전·대상·Host·본문 한도 검사. 본문 바이트 수신은 `conn`에 남긴다.
- `src/downstream/uri.c`: 대상 URI 분리, absolute-form 처리, 경로 퍼센트 디코딩, 경로 정규화.
- `src/downstream/response_writer.c`: 응답 상태 줄·헤더 작성과 chunked 출력.
- `src/downstream/listener.c`: 대기 소켓 열기, 연결 받기, 포트 조회, 소켓 닫기.
- `src/downstream/conn.c`: 연결 하나의 읽기·파싱·라우팅/처리 호출·본문 송수신·연결 유지·자원 정리 흐름.
- `src/downstream/conn.h`: v1/v2 연결 API와 상태·환경 타입을 설명한다. 타입마다 `역할:` 설명을 추가했다.

### 인수인계 자료

- `src/common/README.md`, `src/downstream/README.md`: 기존 파일 책임·테스트 목록과 구현 단계 표시를 갱신했다. v1 blocking 경로는 완료 표시하고 v2 이벤트 경로는 미완료로 남겨 두었다.
- `src/README.md`: 처음 보는 사람을 위한 용어, 처리 흐름, 타입과 공개 함수 안내.
- `src/HANDOFF.md`: 이 문서. 수정 범위, 현재 상태, 미완료 지점과 다음 확인 항목을 기록한다.

## 처리 흐름에서 중요한 설계 규칙

1. `common`은 HTTP 바이트를 해석하고 출력 버퍼를 만든다. 소켓 I/O는 `downstream/conn.c`가 한다.
2. TCP 입력은 여러 조각으로 나뉘거나 여러 요청이 붙어 들어올 수 있다. 파서는 완료 여부를 연결에 알려주며, 연결은 첫 요청이 소비한 바이트만 제거한다.
3. `http_request_t`의 문자열 뷰(`str_t`)는 수신 버퍼를 빌린다. 요청을 처리하는 동안 버퍼를 consume하거나 재할당하면 해당 뷰가 무효가 될 수 있다.
4. 요청 파서는 요청 머리까지만 읽는다. 요청 본문 바이트는 `conn`이 Content-Length에 맞춰 모은다. 현재 요청 파서는 chunked 요청을 501로 거부한다.
5. 처리기는 응답 계획을 만들고, `conn`이 응답 머리를 쓰고 계획에 포함된 본문 자원(fd·버퍼·자식 프로세스·업스트림 연결)을 전송하거나 정리한다.
6. 응답 이후 연결을 유지할 때는 현재 요청이 사용한 바이트만 제거한다. 파이프라이닝으로 다음 요청 바이트가 남아 있으면 곧바로 다음 요청 파싱으로 간다.
7. 타임아웃은 단계별 절대 마감 시각을 기준으로 판단한다. 새 바이트가 조금씩 도착한다는 이유로 헤더 마감을 뒤로 미루지 않는다.

## 현재 미완료 상태

### `downstream` 안에서 확인된 미완료

- v2 `conn_on_event` 경로는 메모리·파일 응답을 처리한다.
- v2에서 CGI pipe를 이벤트 기반으로 진행하는 상태 머신은 아직 연결되지 않았다.
- v2에서 비동기 프록시 relay fd를 이벤트 기반으로 진행하는 상태 머신은 아직 연결되지 않았다. 현재 해당 CGI·프록시 경로는 500 응답으로 끝난다.
- `src/downstream/README.md`의 `conn — 이벤트 경로 (v2)` 항목은 미완료 표시다.

### 이 작업 범위 밖

라우터, 처리기, 업스트림 relay와 실행 엔진의 실제 구현 여부는 이 문서 작성 과정에서 다시 확인하지 않았다. 이들 영역을 수정하지 않았으므로 서버 전체 연결·실행은 다음 작업자가 해당 소스와 빌드 설정을 확인해야 한다.

## 다음 작업자가 진행할 순서

1. 새 안내서와 두 디렉토리 README를 읽고 코드 영역의 경계와 현재 표시를 맞춘다.
2. v2의 CGI와 proxy 경로를 각각 상태 전이로 나누고, 보조 fd의 등록·해제와 timeout·취소·자원 회수 경로를 연결한다.
3. v2 구현 전후로 기존 동작이 바뀌지 않는지, 요청·응답의 부분 읽기/쓰기와 연결 종료 경로를 테스트한다.
4. 각 디렉토리 README에 적힌 테스트 ID와 프로젝트 빌드 절차를 실제로 실행하고 결과를 기록한다. 문서에 나열된 ID는 실행 기록이 아니다.
5. 다른 디렉토리를 수정해야 한다면 작업 범위를 먼저 확인한다. 이 인수인계는 `common`·`downstream`의 경계만 다룬다.

## 검증 기록

- 이 1차 작업에서는 빌드와 테스트를 실행하지 않았다. 따라서 통과한 테스트는 보고하지 않는다.
- 소스 주석은 역할과 주요 경로를 설명하지만, 설명을 추가한 사실 자체는 실행 검증이 아니다.
- 이번 인수인계 문서는 기존 코드와 `common`·`downstream` README를 바탕으로 작성했다. 실제 서버 동작과 이 문서 범위 밖의 세부 상태는 미확인이다.
