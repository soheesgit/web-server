# Stage 7 스레드 풀과 이벤트 루프 비교

## 구현과 실행

- v1 스레드 풀은 워커가 클라이언트 연결을 맡아 처리한다. v2는 하나의 루프에서 클라이언트 소켓, 업스트림 relay, CGI pipe의 준비 이벤트를 받아 상태를 진행한다. macOS는 kqueue, Linux는 epoll을 사용하며 POSIX poll로도 빌드할 수 있다.
- v2는 응답을 작은 조각으로 전달한다. 클라이언트 소켓에 쓰기가 밀리면 소스 읽기를 멈춘다. 이벤트 배치에 이미 들어온 등록 객체는 배치가 끝날 때까지 보존하고, 단조 시계 마감은 최소 힙에서 꺼낸다.
- 정적 파일의 로컬 I/O, 로그 출력, CGI 생성과 회수는 기존 로컬 시스템 호출을 공유한다. v2의 네트워크 대기와 파이프 대기는 poller에 맡긴다. 백엔드 복구 대기열은 D-042 후속 범위다.

```sh
make reverse-proxy ENGINE=loop
make reverse-proxy ENGINE=pool
```

두 명령 모두 Least Requests를 선택하며 기본 설정 파일의 유휴 풀 상한은 8이다. 커스텀 설정 파일의 실행 방법은 [프록시 운영 문서](../PROXY_STAGE4.md)를 참고한다.

## 재현

```sh
make
make test
make test ENGINE=loop
python3 tests/bench/proxy_verify.py --engine loop
python3 tests/bench/worker_bench.py --compare-engines --out /tmp/stage7-engines.jsonl
```

macOS arm64, 논리 CPU 10개, RAM 16 GiB인 한 호스트에서 클라이언트·프록시·백엔드를 루프백으로 연결했다. 같은 바이너리에서 엔진만 바꿨다. **Least Requests·백엔드당 유휴 연결 8개**, 백엔드 응답 지연 1·4·14 ms, 클라이언트 동시성 48을 고정했다. 스레드 풀은 Stage 5 측정에서 유휴 연결 부하에 적합했던 **워커 40개·큐 1,024칸**을 사용했다.

각 실행에서 1 KiB 요청 48개로 워밍업한 뒤, 작은 요청 480개를 보내는 기본 부하에 다음 조건을 각각 적용했다. 엔진 2개 × 조건 4개 × 5회이며 순서는 고정 시드로 섞었다.

- 일반 트래픽
- 미리 응답을 받은 유휴 Keep-Alive 연결 16개
- 미리 응답을 받은 유휴 Keep-Alive 연결 36개
- 각각 8 MiB 응답을 8 MiB/s로 수신하는 클라이언트 6개

[실행별 원본 데이터](stage7-engines-macos.jsonl)

## 측정 결과

성공 RPS와 작은 요청의 완료 P99는 5회 평균 ± 표본 표준편차다. P99는 HTTP 200으로 완료한 1 KiB 요청만 집계했다. RSS는 프록시의 실행별 표본 최대를 평균했다. 두 엔진 모두 503, 기타 HTTP 오류, 수송 오류가 0건이었다.

| 부하 | 엔진 | 성공 RPS | 1 KiB 완료 P99 (ms) | 최대 RSS (MiB) |
|---|---|---:|---:|---:|
| 일반 | 스레드 풀 | 5,361 ± 452 | 23.52 ± 0.59 | 6.04 |
| 일반 | 이벤트 루프 | 5,593 ± 555 | 23.62 ± 1.85 | 4.64 |
| 유휴 Keep-Alive 16개 | 스레드 풀 | 5,033 ± 198 | 22.65 ± 0.69 | 5.79 |
| 유휴 Keep-Alive 16개 | 이벤트 루프 | 4,840 ± 280 | 25.16 ± 1.66 | 5.11 |
| 유휴 Keep-Alive 36개 | 스레드 풀 | 1,057 ± 8 | 58.28 ± 1.34 | 5.92 |
| 유휴 Keep-Alive 36개 | 이벤트 루프 | 4,115 ± 1,046 | 41.25 ± 24.05 | 5.60 |
| 느린 8 MiB 수신 | 스레드 풀 | 5,643 ± 412 | 24.73 ± 2.57 | 6.06 |
| 느린 8 MiB 수신 | 이벤트 루프 | 5,541 ± 223 | 26.05 ± 2.42 | 4.94 |

유휴 연결 36개일 때 스레드 풀에서는 40개 중 36개 워커가 유휴 연결을 맡는다. 이벤트 루프에서는 유휴 소켓이 다음 읽기 이벤트를 기다린다. 이 조건에서 이벤트 루프의 성공 RPS는 **1,057 → 4,115로 3.89배**, P99 평균은 **58.28 → 41.25 ms로 29.22% 감소**했다. 다만 이벤트 루프의 P99는 23.60~82.88 ms로 흔들렸고, 5회 중 1회는 스레드 풀보다 높았다.

일반 부하의 P99는 비슷했고, 유휴 연결 16개와 느린 다운로드 조건의 평균 P99는 스레드 풀이 낮았다. 이벤트 루프의 최대 RSS 표본 평균은 네 조건 모두 낮았다. 수치는 한 호스트의 짧은 루프백 실험이며, Linux에서는 epoll의 기능과 ASan·UBSan을 검증했다. 이기종 백엔드용 실행 프로필은 기존 스레드 풀 기본값과 이벤트 루프 선택지 `ENGINE=loop`를 제공한다.
